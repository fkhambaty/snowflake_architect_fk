Silver layer — clean and filter

Understand this before you copy

Silver applies technical quality: consistent casing, drop bad totals, keep grain one row per event.

SQLPlain English
UPPER(STATUS)Standardize status text
WHERE ORDER_TOTAL >= 0Reject impossible negatives (simple rule demo)
CREATE TABLE … AS SELECTMaterialize silver for reuse (dbt would own this in prod)
Interview: “Silver is trusted operational detail — not yet executive KPIs.”
SQL · silver build
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;

CREATE SCHEMA IF NOT EXISTS MART;

CREATE OR REPLACE TABLE CURATED.SILVER_ORDERS AS
SELECT
  ORDER_ID,
  CUSTOMER_ID,
  UPPER(STATUS) AS STATUS,
  ORDER_TOTAL,
  UPDATED_AT
FROM RAW.ORDERS_EVENTS
WHERE ORDER_TOTAL >= 0;
3

Gold layer — business mart

Understand this before you copy

Gold changes grain: one row per customer with lifetime order count and revenue.

SQLPlain English
GROUP BY CUSTOMER_IDRoll up all silver orders per customer
SUM(ORDER_TOTAL)Lifetime value metric
MAX(UPDATED_AT)Freshness hint for dashboards
Analysts often query gold/mart tables — not bronze JSON blobs.
SQL · gold build
CREATE OR REPLACE TABLE MART.GOLD_ORDER_SUMMARY AS
SELECT
  CUSTOMER_ID,
  COUNT(*) AS ORDER_COUNT,
  SUM(ORDER_TOTAL) AS LIFETIME_VALUE,
  MAX(UPDATED_AT) AS LAST_UPDATE
FROM CURATED.SILVER_ORDERS
GROUP BY CUSTOMER_ID;
4

Prove layer row counts + peek gold

Understand this before you copy

Union counts show bronze ≥ silver (filters) and gold ≤ distinct customers in silver.

If gold has more rows than customers, your GROUP BY grain is wrong.
SQL · layer counts
SELECT 'bronze rows' AS layer, COUNT(*) AS n FROM RAW.ORDERS_EVENTS
UNION ALL
SELECT 'silver rows', COUNT(*) FROM CURATED.SILVER_ORDERS
UNION ALL
SELECT 'gold customers', COUNT(*) FROM MART.GOLD_ORDER_SUMMARY;
SQL · top customers
SELECT * FROM MART.GOLD_ORDER_SUMMARY ORDER BY LIFETIME_VALUE DESC;

Data Vault — interview talktrack (no build)

Use this table when they ask “Medallion or Data Vault?”

Understand this before you memorize

Data Vault 2.0 models hubs (business keys), links (relationships), satellites (attributes/history). It shines when sources change constantly and auditability beats simplicity.

You are not building hubs/links here — you explain tradeoffs like an architect.
TopicMedallion (this lab)Data Vault (talktrack)
Primary goalFast path to analytics layers (bronze/silver/gold)Auditable integration of many changing sources
Model shapeTables/views per layer, often star schema in goldHubs, links, satellites + business keys
HistoryStreams, snapshots, or dbt SCD patterns in silver/goldBuilt-in satellite timelines per source
Team fitAnalytics engineering + BI consumersEnterprise data teams with heavy source churn
When to chooseCloud lakehouse, dbt, clear consumption layersRegulated env, many sources, integration complexity
Interview line“We medallion for delivery speed and clarity.”“We’d DV when traceability and source agility dominate.”

Self-check

  1. What layer is RAW.ORDERS_EVENTS in this lab?
  2. Why materialize silver instead of querying bronze directly in gold SQL?
  3. Name one hub and one satellite in Data Vault terms.
  4. When would you not jump straight to medallion?
Click for short answers
  1. Bronze (raw landing / events).
  2. Reuse cleaning rules; separate concerns; easier testing and lineage.
  3. Hub = business key entity; satellite = descriptive/historical attributes on that key.
  4. Many volatile sources needing full integration audit trail — consider DV or hybrid.
Interview soundbite
“I implement medallion bronze/silver/gold for clarity and speed: raw events, conformed silver, customer-level gold marts. Data Vault is my answer when the problem is integrating dozens of changing sources with strong audit — hubs, links, satellites — often hybrid: DV in the integration zone, medallion marts for consumption.”
