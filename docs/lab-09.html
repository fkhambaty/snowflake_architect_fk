Lab 09 · Friday PM · You are Elena · Dev (QA)

Someone dropped a table — and Dev needs prod-like data

Accidental DELETE and DROP panic the team. Elena uses Time Travel, UNDROP, and zero-copy clone for Dev’s QA sprint.

Business problem A engineer dropped a curated demo table after a bad migration. Dev (QA) also wants prod-like data every sprint without paying double storage upfront.
Solution you will run Query AT/OFFSET, UNDROP, and CREATE TABLE … CLONE for Dev’s sandbox copy.

Clone is same-account fast fork — not geo-DR (Lab 11). Dev runs tests on WH_BANK_XS while prod keeps serving Marcus.

Time Travel, UNDROP, clone

SQL · sql/09_timetravel_clone.sql
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA CURATED;

CREATE OR REPLACE TABLE TT_DEMO (ID NUMBER, NOTE STRING);
INSERT INTO TT_DEMO VALUES (1, 'before');
UPDATE TT_DEMO SET NOTE = 'after' WHERE ID = 1;
DELETE FROM TT_DEMO WHERE ID = 1;
SELECT * FROM TT_DEMO AT (OFFSET => -60*2);

CREATE OR REPLACE TABLE TT_DEMO2 (ID NUMBER, NOTE STRING);
INSERT INTO TT_DEMO2 VALUES (1, 'keep me');
DROP TABLE TT_DEMO2;
UNDROP TABLE TT_DEMO2;
SELECT * FROM TT_DEMO2;

CREATE OR REPLACE TABLE TT_DEMO_CLONE CLONE TT_DEMO2;
SELECT * FROM TT_DEMO_CLONE;
SELECT 'Lab 09 Time Travel / UNDROP / CLONE OK' AS status;
✓ Dev can refresh QA via re-clone on a schedule
Elena’s wrap-up (say this out loud)
“Meridian had operator panic and QA freshness needs. I recovered rows with Time Travel, put dropped tables back with UNDROP, and gave Dev a zero-copy clone of TT_DEMO2. Outcome: minutes to recover mistakes; QA without duplicating full storage on day one.”
