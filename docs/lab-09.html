Lab 09 · Data lifecycle · Understand first, then run

Time Travel, UNDROP & zero-copy clone

Snowflake keeps deleted/changed data for a retention window. You can query the past, recover drops, and clone without doubling storage immediately. UNDROP and CLONE are the most reliable live demos.

After this lab you can explain
  • Time Travel vs Fail-safe (retention vs last-resort)
  • Why AT (OFFSET => …) can fail if you run steps too fast or retention is short
  • UNDROP for “oops I dropped the table”
  • CREATE … CLONE for QA/dev copies (metadata pointer — not a full copy day one)

Retention (read this once)

SettingTypical trial / defaultArchitect note
Time Travel retentionOften 1 day on standard; extend per object/accountQueries using AT only work inside the window
Fail-safe7 days after Time Travel endsSnowflake support recovery — not a self-serve SQL feature for users

If AT (OFFSET => -60*5) errors, your earlier version may already be out of retention — that is a teaching moment, not a lab failure.

1

Time Travel story: insert → update → delete

We mutate data on purpose, then try to see the “before” state.

Understand this before you copy

Step in scriptWhat happened to history
INSERT … 'before'Version 1 exists in Time Travel
UPDATE … 'after'Version 2; version 1 still recoverable for a while
DELETERow gone from “current” table — past versions may still be queryable
Interviews: Time Travel is for logical recovery and audit — not a backup strategy by itself.
SQL · Step 1 · mutate TT_DEMO
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA CURATED;

CREATE OR REPLACE TABLE TT_DEMO (ID NUMBER, NOTE STRING);
INSERT INTO TT_DEMO VALUES (1, 'before');

SET qid = LAST_QUERY_ID();

UPDATE TT_DEMO SET NOTE = 'after' WHERE ID = 1;
DELETE FROM TT_DEMO WHERE ID = 1;

SELECT * FROM TT_DEMO;  -- empty now
2

Query Time Travel (may be flaky — know why)

Offset-based travel assumes “~5 minutes ago” is still retained.

Understand this before you copy

AT (OFFSET => -60*5) means “as of about 5 minutes ago.” If you ran Step 1 seconds ago, the “before delete” state might need AT (TIMESTAMP => …) or BEFORE (STATEMENT => $qid) instead.

Say in interview: “I match the Time Travel predicate to retention and use statement/timestamp when offsets are ambiguous.”
SQL · Step 2 · optional time travel select
-- Try offset (works if retention + timing align)
SELECT * FROM TT_DEMO AT (OFFSET => -60*5);

-- More precise when you saved $qid from INSERT:
-- SELECT * FROM TT_DEMO BEFORE (STATEMENT => $qid);
If this errors — explain retention to the interviewer; move to Step 3 (UNDROP) which always lands well in demos.
3

UNDROP — reliable “save the demo” move

Drop a table, then bring it back within the Time Travel window.

Understand this before you copy

CommandPlain English
DROP TABLE TT_DEMO2Table hidden from catalog — not instantly destroyed
UNDROP TABLE TT_DEMO2Restore name + data if still in Time Travel
Architects mention UNDROP for operator mistakes; long-term DR still needs replication / backups strategy.
SQL · Step 3 · UNDROP demo
CREATE OR REPLACE TABLE TT_DEMO2 (ID NUMBER, NOTE STRING);
INSERT INTO TT_DEMO2 VALUES (1, 'keep me');
DROP TABLE TT_DEMO2;
UNDROP TABLE TT_DEMO2;
SELECT * FROM TT_DEMO2;
✓ Row “keep me” returns — strong interview demo.
4

Zero-copy clone

New table name; shared micro-partitions until you change data.

Understand this before you copy

CREATE TABLE … CLONE … creates a new object pointing at the same storage. Great for QA refresh, what-if testing, and sandbox schemas — without an immediate full copy bill.

Interview tie-in: clone for QA (Lab 14) vs share for partners (Lab 10) vs replicate for DR (Lab 11).
SQL · Step 4 · zero-copy clone
CREATE OR REPLACE TABLE TT_DEMO_CLONE CLONE TT_DEMO2;
SELECT * FROM TT_DEMO_CLONE;

SELECT 'Lab 09 Time Travel / UNDROP / CLONE OK' AS status;
✓

Quick self-check

  1. What is the difference between Time Travel and Fail-safe?
  2. Why might AT (OFFSET => …) fail in a fast lab?
  3. Does clone duplicate all bytes on day one?
Click for short answers
  1. Time Travel is user-queryable history in retention; Fail-safe is Snowflake-managed last resort after that.
  2. Retention window too short, or offset doesn’t point at the version you think.
  3. No — metadata-level pointer; storage diverges as clone or source changes.
60-second interview answer
“Time Travel keeps versions for a configured retention period — I can query AT/BEFORE or restore with UNDROP. I don’t treat it as geo-DR; I use replication for that. For QA I zero-copy clone prod tables or schemas so teams fork without an immediate full storage copy. I always state retention limits when someone asks about compliance recovery.”
