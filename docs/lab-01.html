RBAC like an architect

Rule for this lab: read the blue “Understand this” box → then copy the small SQL under it. Do not paste a giant script blindly. Interviewers ask why, not “can you paste?”

What you will be able to explain after this lab
  • What a role is (a badge of permissions — not a person)
  • Why we use functional roles vs access roles
  • Why analysts get a view instead of the raw table

Big picture (30 seconds)

Naming cheat sheet: FR_* = Functional Role (job). AR_* = Access Role (permissions only).

0

Privilege repair (only if CREATE ROLE failed earlier)

Skip this if Lab 00 already showed “CREATE ROLE smoke test passed”.

Understand this before you copy

Creating roles is an account-level power. Your lab role can own a database, but it cannot create new roles until ACCOUNTADMIN says: “I allow ROLE_ARCH_LAB_ADMIN to create roles.”

SQL ideaPlain English
USE ROLE ACCOUNTADMINPut on the “super admin” badge for this step only
GRANT CREATE ROLE ON ACCOUNT …Allow lab admin to invent new roles
… WITH GRANT OPTIONLab admin can also give warehouse access to others (FR_* roles)
CREATE ROLE … SMOKE_TMP then DROPQuick test: if this fails, stop — privileges still wrong
Why it matters: Without this, Step 2 dies with the error you already saw on account QQ00022.
Role: ACCOUNTADMIN ▾
SQL · Step 0
USE ROLE ACCOUNTADMIN;

GRANT CREATE ROLE ON ACCOUNT TO ROLE ROLE_ARCH_LAB_ADMIN;

GRANT USAGE ON WAREHOUSE WH_ARCH_XS TO ROLE ROLE_ARCH_LAB_ADMIN WITH GRANT OPTION;
GRANT OPERATE ON WAREHOUSE WH_ARCH_XS TO ROLE ROLE_ARCH_LAB_ADMIN WITH GRANT OPTION;

SET uname = (SELECT CURRENT_USER());
GRANT ROLE ROLE_ARCH_LAB_ADMIN TO USER IDENTIFIER($uname);

USE ROLE ROLE_ARCH_LAB_ADMIN;
CREATE ROLE IF NOT EXISTS ROLE_ARCH_SMOKE_TMP COMMENT = 'temp smoke test - safe to drop';
DROP ROLE IF EXISTS ROLE_ARCH_SMOKE_TMP;

SELECT 'Privilege repair OK — CREATE ROLE works for ROLE_ARCH_LAB_ADMIN' AS status;
✓ Must see “Privilege repair OK…” before continuing.
1

Confirm the customer table exists

We only protect data that is actually there.

Understand this before you copy

SQLPlain English
USE ROLE …Which badge am I wearing?
USE WAREHOUSE …Which engine runs my SQL?
USE DATABASE …Which “folder” of objects?
COUNT(*)How many customer rows?
COUNT(SSN_LAST4)How many rows have that PII column filled?
Why: If n ≠ 5, later “analyst blocked” demos mean nothing — you’re testing an empty table.
SQL · Step 1
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
SELECT COUNT(*) AS n, COUNT(SSN_LAST4) AS pii_rows FROM RAW.CUSTOMERS;
✓ Expect n = 5. If 0 → Lab 00 Step 4 (sample data).
2

Create empty roles (name tags only — no powers yet)

Creating a role does not give access by itself. It’s just an empty badge.

Understand this before you copy

CREATE ROLE = “Invent a new badge name.” Nothing can read tables yet.

  • AR_* = Access roles → we will hang permissions on these
  • FR_* = Functional roles → we will hang these on people/jobs
  • IF NOT EXISTS = safe to re-run; won’t crash if the role is already there
Interview line: “Roles are empty until you GRANT something to them.”

Chunk A — create roles

SQL · create AR_* and FR_*
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;

-- Access roles = permission packs
CREATE ROLE IF NOT EXISTS AR_RAW_READ;
CREATE ROLE IF NOT EXISTS AR_CURATED_READ;
CREATE ROLE IF NOT EXISTS AR_PII_READ;

-- Functional roles = job badges
CREATE ROLE IF NOT EXISTS FR_ANALYST;
CREATE ROLE IF NOT EXISTS FR_DATA_ENGINEER;
CREATE ROLE IF NOT EXISTS FR_COMPLIANCE;
3

Give warehouse power to job roles

Even SELECT needs a warehouse (compute). No warehouse usage → query can’t run.

Understand this before you copy

GRANT USAGE ON WAREHOUSE … TO ROLE FR_ANALYST means: “The Analyst badge is allowed to use this tiny warehouse engine.”

We grant this to FR_* (people/jobs), not only to access roles, because the person switches into FR_ANALYST and needs compute immediately.

This is why Lab 00 gave lab admin WITH GRANT OPTION — so it can pass warehouse usage along.
SQL · warehouse to FR_*
GRANT USAGE ON WAREHOUSE WH_ARCH_XS TO ROLE FR_ANALYST;
GRANT USAGE ON WAREHOUSE WH_ARCH_XS TO ROLE FR_DATA_ENGINEER;
GRANT USAGE ON WAREHOUSE WH_ARCH_XS TO ROLE FR_COMPLIANCE;
4

Unlock the “doors” (database + schema USAGE)

Snowflake is like a building: you need keys for the building, then the floor, then the room.

Understand this before you copy

  • Database USAGE = enter the building (ARCH_INTERVIEW)
  • Schema USAGE = enter the floor (RAW / CURATED)
  • SELECT on table/view = open a specific room (next step)

If you only GRANT SELECT on a table but forget schema USAGE, Snowflake still blocks you. Beginners get burned by this constantly.

Interview line: “Privileges are hierarchical — USAGE on container objects, then object privileges.”
SQL · database + schema USAGE
GRANT USAGE ON DATABASE ARCH_INTERVIEW TO ROLE AR_RAW_READ;
GRANT USAGE ON DATABASE ARCH_INTERVIEW TO ROLE AR_CURATED_READ;
GRANT USAGE ON DATABASE ARCH_INTERVIEW TO ROLE AR_PII_READ;

GRANT USAGE ON SCHEMA RAW TO ROLE AR_RAW_READ;
GRANT USAGE ON SCHEMA CURATED TO ROLE AR_CURATED_READ;
GRANT USAGE ON SCHEMA SECURE TO ROLE AR_PII_READ;
GRANT USAGE ON SCHEMA RAW TO ROLE AR_PII_READ;
Notice We put USAGE on AR_* (access packs), not directly on every human. Humans inherit these packs in a later step.
5

Grant SELECT on tables (the actual data permission)

Now the access roles can read data — still not given to humans yet.

Understand this before you copy

SQLPlain English
GRANT SELECT ON ALL TABLES IN SCHEMA RAW … Read every table that exists today in RAW
GRANT SELECT ON FUTURE TABLES IN SCHEMA RAW … Also auto-allow tables created later — so you don’t forget tomorrow

AR_CURATED_READ gets curated schema tables. AR_RAW_READ / AR_PII_READ get RAW (PII lives there in this lab).

Interview gold: “I use future grants so new tables don’t silently become invisible — or accidentally open — without a plan.”
SQL · SELECT + future grants
GRANT SELECT ON ALL TABLES IN SCHEMA RAW TO ROLE AR_RAW_READ;
GRANT SELECT ON FUTURE TABLES IN SCHEMA RAW TO ROLE AR_RAW_READ;

GRANT SELECT ON ALL TABLES IN SCHEMA CURATED TO ROLE AR_CURATED_READ;
GRANT SELECT ON FUTURE TABLES IN SCHEMA CURATED TO ROLE AR_CURATED_READ;

GRANT SELECT ON ALL TABLES IN SCHEMA RAW TO ROLE AR_PII_READ;
GRANT SELECT ON FUTURE TABLES IN SCHEMA RAW TO ROLE AR_PII_READ;
6

Wire job badges → permission packs (the architect graph)

This is the most important mental model in the whole lab.

Understand this before you copy

GRANT ROLE AR_CURATED_READ TO ROLE FR_ANALYST means:

“Whoever wears Analyst also wears the curated-read pack.”

  • Analyst → curated only (safe)
  • Engineer → raw + curated (pipelines)
  • Compliance → PII + curated

We do not grant table SELECT directly to FR_ANALYST. That keeps the design clean when 50 analysts join.

Interview line: “Functional roles for people/groups; access roles for privileges; grant access→functional, not tables→every human.”
FR_ANALYST
inherits
AR_CURATED_READ
↛
AR_PII_READ
SQL · grant access roles to functional roles
GRANT ROLE AR_CURATED_READ TO ROLE FR_ANALYST;

GRANT ROLE AR_RAW_READ TO ROLE FR_DATA_ENGINEER;
GRANT ROLE AR_CURATED_READ TO ROLE FR_DATA_ENGINEER;

GRANT ROLE AR_PII_READ TO ROLE FR_COMPLIANCE;
GRANT ROLE AR_CURATED_READ TO ROLE FR_COMPLIANCE;
7

Give those job badges to YOU (so you can test)

Roles exist in the account, but your user must be allowed to wear them.

Understand this before you copy

SQLPlain English
SET uname = (SELECT CURRENT_USER());Store my login name in a variable
GRANT ROLE FR_ANALYST TO USER …Allow Faizan (you) to switch into Analyst
IDENTIFIER($uname)Use that variable as the real username safely

In real companies, an IdP group (Okta/Azure AD) often maps to FR_ANALYST automatically. Here we grant to your user so the dropdown shows the roles.

If the role is missing from the Snowsight dropdown, this step didn’t stick (or UI needs a refresh).
SQL · grant FR_* to your user
SET uname = (SELECT CURRENT_USER());
GRANT ROLE FR_ANALYST TO USER IDENTIFIER($uname);
GRANT ROLE FR_DATA_ENGINEER TO USER IDENTIFIER($uname);
GRANT ROLE FR_COMPLIANCE TO USER IDENTIFIER($uname);
8

Create the “safe window” view (no PII columns)

A view is a saved SELECT. Analysts look through the window — not into the whole room.

Understand this before you copy

Raw table has: name, email, phone, SSN last-4, …

View keeps only: CUSTOMER_ID, FULL_NAME, COUNTRY, CREATED_AT

Then we grant SELECT on the view to AR_CURATED_READ.

Important: even if someone somehow reached the view definition, they still need privileges. The main win here is column exclusion + RBAC so analysts never get RAW.

Later labs add masking policies (hide SSN even for roles that can SELECT the table). RBAC + views is the first layer.
SQL · curated view
USE SCHEMA CURATED;

CREATE OR REPLACE VIEW V_CUSTOMERS_PUBLIC AS
SELECT
  CUSTOMER_ID,
  FULL_NAME,
  COUNTRY,
  CREATED_AT
FROM RAW.CUSTOMERS;

GRANT SELECT ON VIEW V_CUSTOMERS_PUBLIC TO ROLE AR_CURATED_READ;

SELECT 'Safe view ready' AS status;
9

Prove it: Analyst can see safe data, not PII

This is the interview demo. Change the Role chip or it’s fake.

Understand this before you copy

USE ROLE FR_ANALYST = “I am now wearing only the Analyst badge.”

Snowflake re-checks every permission from that badge’s inheritance chain.

  • View query → should work (inherits AR_CURATED_READ → SELECT on view)
  • RAW table → should fail (never inherited AR_RAW_READ / AR_PII_READ)
Saying “we secured it” is weak. Showing a failed SELECT on RAW is strong.
Role: FR_ANALYST ▾
WH: WH_ARCH_XS ▾
DB: ARCH_INTERVIEW ▾

A — should work

SQL · analyst safe
USE ROLE FR_ANALYST;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
SELECT * FROM CURATED.V_CUSTOMERS_PUBLIC;
✓ Columns: id, name, country, created — no email/phone/SSN

B — should fail (red error = you did it right)

SQL · analyst blocked
SELECT * FROM RAW.CUSTOMERS;
✗ Insufficient privileges — celebrate this error
10

Prove Engineer and Compliance paths

Same person (you), different badges → different powers. That’s RBAC.

Understand this before you copy

You are not creating three Snowflake users. You are switching roles.

That’s normal in Snowflake: one human, many roles; primary role decides the privilege set (unless secondary roles are enabled — advanced topic for later).

SQL · engineer
USE ROLE FR_DATA_ENGINEER;
SELECT CUSTOMER_ID, EMAIL FROM RAW.CUSTOMERS LIMIT 5;
✓ Engineer can read RAW (pipeline work).
SQL · compliance
USE ROLE FR_COMPLIANCE;
SELECT CUSTOMER_ID, SSN_LAST4 FROM RAW.CUSTOMERS;
✓ Compliance can read PII.
11

Read the wiring with SHOW GRANTS

Architects can explain the graph from Snowflake itself — not from memory alone.

Understand this before you copy

CommandQuestion it answers
SHOW GRANTS TO ROLE FR_ANALYSTWhat did Analyst receive? (should include role AR_CURATED_READ)
SHOW GRANTS TO ROLE AR_CURATED_READWhat can the curated pack do? (USAGE/SELECT…)
SHOW GRANTS OF ROLE AR_CURATED_READWho/what was given this pack? (FR_ANALYST, etc.)
In interviews: “I’d verify with SHOW GRANTS / ACCESS_HISTORY — not assume.”
SQL · inspect grants
USE ROLE ROLE_ARCH_LAB_ADMIN;
SHOW GRANTS TO ROLE FR_ANALYST;
SHOW GRANTS TO ROLE AR_CURATED_READ;
SHOW GRANTS OF ROLE AR_CURATED_READ;
✓

Quick self-check (no Snowflake needed)

If you can answer these, you understood — not just pasted.

  1. Why create AR_CURATED_READ instead of granting the view straight to every analyst user?
  2. Why does Analyst need schema USAGE and SELECT?
  3. What does GRANT ROLE A TO ROLE B mean in one sentence?
  4. Why is a failed SELECT on RAW.CUSTOMERS as Analyst a success?
Click for short answers
  1. One permission pack → many people/jobs; easier to audit and change once.
  2. Snowflake checks container access (db/schema) before object access (table/view).
  3. B inherits A’s privileges (role hierarchy).
  4. It proves least privilege: analyst path cannot reach PII tables.
60-second interview answer (now you know why each piece exists)
“I separate functional roles from access roles. Table privileges go on access roles. Analysts inherit curated-read and query a view without PII columns. Engineers inherit raw for pipelines; compliance inherits PII. I prove it by switching to FR_ANALYST — curated view works, RAW select fails. Future grants keep new tables under the same model.”
