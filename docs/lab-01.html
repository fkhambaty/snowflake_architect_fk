Lab 01 · A story first · Then the same SQL as before

The SnowShop vault

Forget “RBAC” for a minute. We’re running a tiny online shop called SnowShop. Customer secrets sit in a vault. You will hire three kinds of workers and hand out the right keys — using the SQL below (unchanged). Read the orange story boxes. Then copy.

Previously (Lab 00) — in one paragraph

You built SnowShop’s private workshop: a building named ARCH_INTERVIEW, a small engine WH_ARCH_XS, and a workshop manager badge ROLE_ARCH_LAB_ADMIN. Inside the building you put rooms (schemas) and locked five fake customers into the back room RAW.CUSTOMERS — including emails and SSN last-4. That back room is the vault.

Today’s story — the whole lab in 60 seconds

The boss says: “Analysts need customer names for charts. Engineers need the messy vault to build pipelines. Compliance needs SSN for audits. Nobody else should wander the vault.”

You will not give each person random keys forever. You invent two kinds of plastic badges:

  • Job badges (FR_*) — “I am an Analyst / Engineer / Compliance”
  • Key-rings (AR_*) — “This ring opens the safe window / the vault / the PII drawer”

Then you clip key-rings onto job badges. When you wear “Analyst”, you only get the safe key-ring. When Snowflake says Insufficient privileges on the vault — the story worked. Celebrate.

Story: print blank badges (no powers yet)

Empty plastic cards with names on them.

Story

You print six blank badges. Three are key-rings (AR_*): “vault reader”, “safe-window reader”, “PII reader”. Three are job titles (FR_*): Analyst, Engineer, Compliance. Right now none of them open anything. They’re just labeled plastic.

USE WAREHOUSE WH_ARCH_XS;

-- Access roles = permission packs
CREATE ROLE IF NOT EXISTS AR_RAW_READ;

Story: open the cabinets (SELECT)

Now the key-rings can open filing cabinets on those floors.

Story

AR_RAW_READ / AR_PII_READ → can open cabinets on the RAW vault floor.
AR_CURATED_READ → can open cabinets on the CURATED floor.
“FUTURE TABLES” means: if someone adds a new cabinet tomorrow, the same key-ring still works — you don’t reprint keys every week.

Still nobody human has a job badge clipped to these rings. That’s next.

SQL · SELECT + future grants
GRANT SELECT ON ALL TABLES IN SCHEMA RAW TO ROLE AR_RAW_READ;
GRANT SELECT ON FUTURE TABLES IN SCHEMA RAW TO ROLE AR_RAW_READ;

GRANT SELECT ON ALL TABLES IN SCHEMA CURATED TO ROLE AR_CURATED_READ;
GRANT SELECT ON FUTURE TABLES IN SCHEMA CURATED TO ROLE AR_CURATED_READ;

GRANT SELECT ON ALL TABLES IN SCHEMA RAW TO ROLE AR_PII_READ;
GRANT SELECT ON FUTURE TABLES IN SCHEMA RAW TO ROLE AR_PII_READ;

Story: build the “reception window”

Analysts never enter the vault — they look through a window.

Story

In the CURATED room you install a glass window named V_CUSTOMERS_PUBLIC. Through the glass you only see: id, name, country, created date. Email, phone, SSN stay in the vault behind the wall. Then you hang “look through this window” on the safe-window key-ring.

SQL · curated view
USE SCHEMA CURATED;

CREATE OR REPLACE VIEW V_CUSTOMERS_PUBLIC AS
SELECT
  CUSTOMER_ID,
  FULL_NAME,
  COUNTRY,
  CREATED_AT
FROM RAW.CUSTOMERS;

GRANT SELECT ON VIEW V_CUSTOMERS_PUBLIC TO ROLE AR_CURATED_READ;

SELECT 'Safe view ready' AS status;

Can you retell the story? (no SQL)

  1. What is a job badge vs a key-ring in one sentence each?
  2. Why does Analyst look through a window instead of entering the vault?
  3. Why is a red “Insufficient privileges” on RAW a happy ending?
Click for short answers
  1. Job badge = who you are at work; key-ring = which doors that job may open.
  2. So they get useful columns without email/phone/SSN.
  3. It proves the Analyst path cannot open the vault — least privilege works.
Interview soundbite (tell the SnowShop story in grown-up words)
“I separate functional roles from access roles. Table privileges go on access roles. Analysts inherit curated-read and query a view without PII. Engineers inherit raw for pipelines; compliance inherits PII. I prove it — FR_ANALYST can select the view; RAW select fails.”
