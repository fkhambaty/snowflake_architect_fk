What this does

Create the secure view (column minimum)

Step 2 · coach

Secure view first

What this does

Exposes only txn fields Nora needs — no BRONZE_LANDING.CLIENTS, no SSN, no email.

Why SECURE

Consumers cannot inspect view SQL to reverse-engineer hidden joins or columns.

SQL · V_SHARE_TXNS
CREATE OR REPLACE SECURE VIEW SILVER_CURATED.V_SHARE_TXNS AS
SELECT TXN_ID, CLIENT_ID, STATUS, AMOUNT
FROM BRONZE_LANDING.TXN_EVENTS;
✓ View under SILVER_CURATED — four columns only

4

Grant database + schema + view to the share

Step 4 · coach

Why grant objects onto the share?

What this does

Consumers need USAGE on database and schema, then SELECT on the view. Without all three, Nora sees nothing.

SQL · share grants
GRANT USAGE ON DATABASE MERIDIAN_BANK TO SHARE SHARE_MERIDIAN_TXNS;
GRANT USAGE ON SCHEMA SILVER_CURATED TO SHARE SHARE_MERIDIAN_TXNS;
GRANT SELECT ON VIEW SILVER_CURATED.V_SHARE_TXNS TO SHARE SHARE_MERIDIAN_TXNS;
✓ Share lists granted objects in Snowsight (provider account)

Create Nora’s login (reader account) — or use a second trial

Step 6 · coach

Another user ≠ Nora

Two ways to be “Nora”

A · Reader account (solo lab — recommended): Meridian creates a managed reader account. You get a second Snowsight URL + user. Reader can only consume Meridian’s shares. Credits for Nora’s warehouse bill Meridian — fine for practice; say that honestly in interviews.

B · Real second Snowflake account: Sign up another free trial as Nora’s credit union. She pays her own warehouse. This matches production billing. Skip the CREATE MANAGED ACCOUNT below; use her account locator in Step 7.

Not a path: Creating user NORA inside MERIDIAN_BANK. That’s Lab 01 RBAC, not Secure Data Sharing.

Trial gotcha: Some personal trials block provider sharing / managed accounts. If CREATE MANAGED ACCOUNT fails, use Path B (second trial) or finish Steps 1–5 and speak the consumer steps aloud for the interview.
SQL · Path A — create Nora reader (ACCOUNTADMIN)
USE ROLE ACCOUNTADMIN;

-- Pick your own strong password; do not commit real passwords to git.
-- Re-run fails if name exists — DROP MANAGED ACCOUNT NA_NORA_READER; first if needed
CREATE MANAGED ACCOUNT NA_NORA_READER
  ADMIN_NAME = 'nora_admin'
  , ADMIN_PASSWORD = 'ChangeMe_NoraLab1!'
  , TYPE = READER
  , COMMENT = 'Lab 10 Nora consumer practice';

SHOW MANAGED ACCOUNTS;
-- Result includes account locator + login URL. Save both.
✓ Reader locator saved · or Path B second-trial locator ready
7

Attach Nora’s account to the share

Step 7 · coach

Whitelist Nora’s locator

What this does

Stocked share still invisible until you whitelist the consumer account. Usually run as ACCOUNTADMIN (needs share ownership + manage-share-target powers).

SQL · whitelist Nora
USE ROLE ACCOUNTADMIN;

-- Paste locator from SHOW MANAGED ACCOUNTS (or Nora’s second-trial locator)
ALTER SHARE SHARE_MERIDIAN_TXNS ADD ACCOUNTS = NORA_LOCATOR_HERE;

SHOW SHARES LIKE 'SHARE_MERIDIAN_TXNS';
-- “to” column should list Nora’s locator
✓ Share targets Nora · now switch browser login
8

Log in as Nora — open the window and SELECT

Step 8 · coach

Log in as Nora

Consumer bootstrap

Open the reader (or second-trial) Snowsight URL. Sign in as nora_admin (or Nora’s trial user). New account is empty until she creates a warehouse and a database from the share.

SQL · Nora account — warehouse + import share
USE ROLE ACCOUNTADMIN;

CREATE WAREHOUSE IF NOT EXISTS WH_NORA_XS
  WAREHOUSE_SIZE = 'XSMALL'
  AUTO_SUSPEND = 60
  AUTO_RESUME = TRUE
  INITIALLY_SUSPENDED = TRUE;

-- Paste Meridian locator from Step 5 (CURRENT_ACCOUNT on provider)
CREATE DATABASE IF NOT EXISTS NORA_FROM_MERIDIAN
  FROM SHARE MERIDIAN_LOCATOR_HERE.SHARE_MERIDIAN_TXNS;

GRANT IMPORTED PRIVILEGES ON DATABASE NORA_FROM_MERIDIAN TO ROLE ACCOUNTADMIN;
USE WAREHOUSE WH_NORA_XS;
USE DATABASE NORA_FROM_MERIDIAN;

SHOW VIEWS;
SELECT * FROM SILVER_CURATED.V_SHARE_TXNS LIMIT 20;
Reader billing: Path A warehouse credits hit Meridian — set a resource monitor if you leave it running. Cleanup (provider): DROP MANAGED ACCOUNT NA_NORA_READER; when done practicing.
✓ Nora sees txn rows · vault CLIENTS not on the share

Interviewer presses further — say these out loud

Basics got you into the room. Cover each answer before you open it. If you blank here, an Architect + dbt interviewer will know.

Q1. Why SECURE view V_SHARE_TXNS instead of sharing the base table?

Say: Secure hides definition and forces the trimmed column list — no BRONZE_LANDING vault, no join logic leakage. Sharing base tables invites SELECT * of tomorrow’s PII. Least columns on a secure view is the partner contract.

Q2. Who pays compute when Nora queries the share?

Say: If Nora has her own Snowflake account — she pays her warehouse. If we provision a reader account for her — Meridian pays reader compute. Failure mode: Meridian running Nora’s reports on WH_BANK_XS “as a courtesy,” or forgetting a monitor on a reader warehouse.

Q3. Share revoked — what still hurts?

Say: Cached extracts Nora already pulled, and any insecure objects once shared. Governance is ongoing: column review, secure view, CREATE SHARE discipline, no “temporary” share of CLIENTS. Clone is wrong here — same-account QA, not cross-org.

Q4. Masking on provider objects — what does Nora see?

Say: Don’t assume her roles map to FR_COMPLIANCE. Share only non-PII txn fields so we don’t rely on her role names matching ours. Cross-account role mapping is designed explicitly, not inherited from Lab 03.

Q5. Can I share with another user in my Meridian account?

Say: No — that’s RBAC/views (Lab 01). Secure Data Sharing is account-to-account. For a solo lab I create a reader account (or a second trial), ALTER SHARE ADD ACCOUNTS, then log in as that consumer and CREATE DATABASE … FROM SHARE.

Q6. Trial limitation you’d call out?

Say: Some trials block managed accounts or provider sharing. I still show the secure view + share grants, then either use a second trial as Nora or narrate the consumer CREATE DATABASE FROM SHARE — same honesty as Lab 11.
