Load Day-1 source rows (raw landing)

dbt transforms data — something else usually lands it. Here that “something” is you + SQL.

Understand this before you copy

SQLPlain English
CREATE TABLE ORDERS_EVENTSLanding table for order changes (like a mini CDC feed)
ORDER_IDBusiness key — same order over time
UPDATED_ATWatermark column — when this version of the order happened
INSERT … 5 rowsFake “Day 1” batch
If UPDATED_AT doesn’t move when status changes, incremental merge will miss updates. That’s a classic production bug.
SQL · Day 1
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA RAW;

CREATE OR REPLACE TABLE ORDERS_EVENTS (
  ORDER_ID     NUMBER,
  CUSTOMER_ID  NUMBER,
  STATUS       STRING,
  ORDER_TOTAL  NUMBER(12,2),
  UPDATED_AT   TIMESTAMP_NTZ
);

INSERT INTO ORDERS_EVENTS VALUES
  (1001, 1, 'CREATED',   40.00, '2026-10-01 10:00:00'),
  (1002, 2, 'CREATED',   15.50, '2026-10-01 11:00:00'),
  (1003, 3, 'SHIPPED',   99.00, '2026-10-01 12:00:00'),
  (1004, 4, 'CREATED',   22.00, '2026-10-01 13:00:00'),
  (1005, 5, 'CANCELLED', 10.00, '2026-10-01 14:00:00');

SELECT 'day1' AS batch, COUNT(*) AS n FROM ORDERS_EVENTS;
✓ n = 5

Read the dbt model (don’t run yet — understand)

Open dbt_project/models/marts/fct_orders_incremental.sql in VS Code while you read this.

Line-by-line: the config block

CodeMeaning
materialized='incremental'First run builds a table; later runs only apply deltas
unique_key='order_id'Match rows by order id when merging
incremental_strategy='merge'On Snowflake, generate a MERGE (upsert), not delete+insert of everything

Line-by-line: the SELECT + watermark

CodeMeaning
{{ ref('stg_orders') }}Read from the staging model (dbt dependency graph)
{% if is_incremental() %}This filter runs only on run #2, #3, … not the first build
updated_at > max(updated_at) from {{ this }}Only rows newer than what’s already in the target table
{{ this }}Fancy name for “the table this model is building”
coalesce(..., '1900-01-01')If target empty, treat max as ancient date so all rows qualify
First run: no filter → load all. Second run: filter + MERGE → cheap updates.
dbt SQL · for reading (already in repo)
{{
  config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
  )
}}

select
    order_id,
    customer_id,
    status,
    order_total,
    updated_at
from {{ ref('stg_orders') }}

{% if is_incremental() %}
  where updated_at > (
    select coalesce(max(updated_at), '1900-01-01'::timestamp_ntz)
    from {{ this }}
  )
{% endif %}

What about stg_orders?

It’s a simple view: select columns from RAW.ORDERS_EVENTS. Staging = “rename/cast/clean lightly.” Marts = “business facts.” Keeping them separate is a dbt habit interviewers expect.

First dbt run — build the table

dbt compiles your model into Snowflake SQL, then runs it.

Understand the commands

CommandMeaning
dbt run --select …Build only these models (faster than whole project)
dbt test --select …Run tests from schema.yml (unique / not_null on order_id)
Tests are how you prove the merge didn’t create duplicate order ids.
Terminal · first run
dbt run --select stg_orders fct_orders_incremental
dbt test --select fct_orders_incremental
SQL · verify
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE DATABASE ARCH_INTERVIEW;
SELECT COUNT(*) AS rows_after_first_run FROM CURATED.FCT_ORDERS_INCREMENTAL;
SELECT * FROM CURATED.FCT_ORDERS_INCREMENTAL ORDER BY ORDER_ID;
✓ 5 rows. Order 1001 status = CREATED

Day 2 changes + second run (the point of the lab)

Two new orders + one status change with a newer UPDATED_AT.

Understand this before you copy

  • INSERT 1006, 1007 → brand new keys → MERGE will insert
  • UPDATE 1001 to SHIPPED + bump UPDATED_AT → MERGE will update that key
  • If you forgot to bump UPDATED_AT, the watermark filter would skip 1001 — status would stay CREATED (bug)
SQL · Day 2
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA RAW;

INSERT INTO ORDERS_EVENTS VALUES
  (1006, 1, 'CREATED', 55.00, '2026-10-02 09:00:00'),
  (1007, 2, 'CREATED', 18.00, '2026-10-02 09:30:00');

UPDATE ORDERS_EVENTS
SET STATUS = 'SHIPPED', UPDATED_AT = '2026-10-02 10:00:00'
WHERE ORDER_ID = 1001;

SELECT ORDER_ID, STATUS, UPDATED_AT FROM ORDERS_EVENTS ORDER BY ORDER_ID;

What the second dbt run does

Because the table already exists, is_incremental() is true → watermark filter applies → Snowflake runs a MERGE on those few rows instead of rebuilding all history.

Terminal · second run
dbt run --select fct_orders_incremental
SQL · prove merge
SELECT ORDER_ID, STATUS, UPDATED_AT
FROM CURATED.FCT_ORDERS_INCREMENTAL
ORDER BY ORDER_ID;
  • 7 rows total (not 10, not duplicates)
  • 1001 is SHIPPED
  • 1006 and 1007 exist

Cost talking point + self-check

In Query History, what are you looking for?

Run #2 should show a statement type around MERGE into the fact table. That’s your proof you didn’t full-scan rebuild for fun.

When NOT incremental: tiny dims; logic changing constantly; full refresh still cheap and safer.
  1. What does unique_key prevent if the same order_id arrives twice?
  2. Why bump UPDATED_AT when status changes?
  3. What’s the difference between staging and marts in one sentence?
Click for short answers
  1. Duplicate fact rows — merge updates the same key instead.
  2. So the watermark filter includes that row on the next incremental run.
  3. Staging cleans/sources; marts are business-ready tables analysts use.
Interview soundbite (you know why each knob exists)
“I use dbt incremental merge on Snowflake with order_id as unique_key and updated_at as watermark. First run builds; later runs merge only new/changed rows. I prove with tests and Query History MERGE. Landing stays in RAW; marts in CURATED behind the same RBAC model.”
