Lab 02 · Domain 3 + dbt · ~40 minutes

dbt incremental merge on Snowflake

Story in one line: Day 1 load 5 orders. Run dbt. Day 2 add 2 orders + update 1. Run dbt again. Table grows correctly — it does not rebuild everything from scratch.

RAW.ORDERS_EVENTS
→
stg_orders
→
fct_orders_incremental (MERGE)
Words you will say in interviews
  • Incremental = only process new/changed rows after the first run
  • Merge = insert new keys, update existing keys (upsert)
  • unique_key = how dbt knows which row is “the same order”
  • Watermark = usually updated_at — “give me rows newer than what I already have”

Point dbt at your Snowflake account

One-time config on your laptop.

  1. Open folder dbt_project from this repo in VS Code.
  2. Open (or create) your profiles file:
    C:\Users\YOURNAME\.dbt\profiles.yml
  3. Copy the template below into that file and fill the blanks.
YAML · profiles.yml template
snowflake_architect_fk:
  target: dev
  outputs:
    dev:
      type: snowflake
      account: YOUR_ACCOUNT_LOCATOR
      user: YOUR_USER
      password: YOUR_PASSWORD
      role: ROLE_ARCH_LAB_ADMIN
      database: ARCH_INTERVIEW
      warehouse: WH_ARCH_XS
      schema: CURATED
      threads: 4
Terminal · test connection
cd dbt_project
dbt debug
✓ All connection checks should be green / OK before continuing.
Don’t put real passwords in Git profiles.yml stays in your user folder — never commit it to the repo.

Load Day-1 orders in Snowflake

Snowsight worksheet, role ROLE_ARCH_LAB_ADMIN.

SQL · Day 1 source load
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA RAW;

CREATE OR REPLACE TABLE ORDERS_EVENTS (
  ORDER_ID     NUMBER,
  CUSTOMER_ID  NUMBER,
  STATUS       STRING,
  ORDER_TOTAL  NUMBER(12,2),
  UPDATED_AT   TIMESTAMP_NTZ
);

INSERT INTO ORDERS_EVENTS VALUES
  (1001, 1, 'CREATED',   40.00, '2026-10-01 10:00:00'),
  (1002, 2, 'CREATED',   15.50, '2026-10-01 11:00:00'),
  (1003, 3, 'SHIPPED',   99.00, '2026-10-01 12:00:00'),
  (1004, 4, 'CREATED',   22.00, '2026-10-01 13:00:00'),
  (1005, 5, 'CANCELLED', 10.00, '2026-10-01 14:00:00');

SELECT 'day1' AS batch, COUNT(*) AS n FROM ORDERS_EVENTS;
✓ Expect n = 5

4

Day 2 deltas → second dbt run (the interview moment)

New orders arrive. One old order ships. Then merge.

SQL · Day 2 changes
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA RAW;

INSERT INTO ORDERS_EVENTS VALUES
  (1006, 1, 'CREATED', 55.00, '2026-10-02 09:00:00'),
  (1007, 2, 'CREATED', 18.00, '2026-10-02 09:30:00');

UPDATE ORDERS_EVENTS
SET STATUS = 'SHIPPED', UPDATED_AT = '2026-10-02 10:00:00'
WHERE ORDER_ID = 1001;

SELECT ORDER_ID, STATUS, UPDATED_AT FROM ORDERS_EVENTS ORDER BY ORDER_ID;
Terminal · second dbt run
dbt run --select fct_orders_incremental
SQL · prove merge worked
SELECT ORDER_ID, STATUS, UPDATED_AT
FROM CURATED.FCT_ORDERS_INCREMENTAL
ORDER BY ORDER_ID;
  • Row count is 7 (not 10, not doubled junk)
  • Order 1001 status is SHIPPED (updated, not duplicated)
  • Orders 1006 and 1007 exist
5

What to say about cost (architect level)

Open Snowsight → Activity / Query History and find the second MERGE.

Activity → Query History
Look for MERGE into FCT_ORDERS…

First run often looks like a full create/insert. Second run should show a MERGE — that is your talking point.

When NOT to use incremental Tiny dimension tables, or when business logic changes so often that full refresh is safer and still cheap.
Interview soundbite
“For facts with daily deltas I use dbt incremental merge on Snowflake with a unique order_id and updated_at watermark. First run builds the table; later runs merge only changes. I validate with uniqueness tests and check Query History for MERGE, not full rebuilds. RAW stays restricted; curated marts are what analysts get — same RBAC story as Lab 01.”
