Day 1 — load transaction events at the dock

Why UPDATED_AT matters

Incremental merge only re-processes rows newer than the fact’s max updated_at. If Jordan updates status but forgets to bump the timestamp, the fact stays wrong — a classic production bug.

SQL · sql/02_orders_source.sql
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA LANDING;

CREATE OR REPLACE TABLE TXN_EVENTS (
  TXN_ID       NUMBER,
  CLIENT_ID    NUMBER,
  STATUS       STRING,
  AMOUNT       NUMBER(12,2),
  UPDATED_AT   TIMESTAMP_NTZ
);

INSERT INTO TXN_EVENTS VALUES
  (1001, 1, 'POSTED',    40.00, '2026-10-01 10:00:00'),
  (1002, 2, 'POSTED',    15.50, '2026-10-01 11:00:00'),
  (1003, 3, 'SETTLED',   99.00, '2026-10-01 12:00:00'),
  (1004, 4, 'POSTED',    22.00, '2026-10-01 13:00:00'),
  (1005, 5, 'REVERSED',  10.00, '2026-10-01 14:00:00');

SELECT 'day1' AS batch, COUNT(*) AS n FROM TXN_EVENTS;
✓ n = 5 in LANDING.TXN_EVENTS

Read the dbt graph (staging → mart)

stg_orders is a view: reads {{ source('landing', 'txn_events') }}, renames txn_id → order_id for the mart contract. Marts = business facts Alex trusts.

dbt · stg_orders.sql + fct_orders_incremental.sql
-- stg_orders.sql (view)
select txn_id as order_id, client_id as customer_id, status,
       amount as order_total, updated_at
from {{ source('landing', 'txn_events') }}

-- fct_orders_incremental.sql (incremental merge)
{{ config(materialized='incremental', unique_key='order_id', incremental_strategy='merge') }}
select order_id, customer_id, status, order_total, updated_at
from {{ ref('stg_orders') }}
{% if is_incremental() %}
  where updated_at > (select coalesce(max(updated_at), '1900-01-01'::timestamp_ntz) from {{ this }})
{% endif %}

Day 2 — new txns + status change, then second run

This is the whole point

Two inserts + one update with a newer UPDATED_AT. Second dbt run should MERGE only those rows — not rebuild history.

SQL · sql/02_orders_day2.sql
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA LANDING;

INSERT INTO TXN_EVENTS VALUES
  (1006, 1, 'POSTED', 55.00, '2026-10-02 09:00:00'),
  (1007, 2, 'POSTED', 18.00, '2026-10-02 09:30:00');

UPDATE TXN_EVENTS
SET STATUS = 'SETTLED', UPDATED_AT = '2026-10-02 10:00:00'
WHERE TXN_ID = 1001;

SELECT TXN_ID, STATUS, UPDATED_AT FROM TXN_EVENTS ORDER BY TXN_ID;
Terminal · second run
dbt run --select fct_orders_incremental
SQL · prove merge
SELECT ORDER_ID, STATUS, UPDATED_AT
FROM CURATED.FCT_ORDERS_INCREMENTAL ORDER BY ORDER_ID;
  • 7 rows total (no duplicates)
  • 1001 is SETTLED
  • 1006 and 1007 exist
