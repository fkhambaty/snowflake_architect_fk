Stop rebuilding the transaction ledger every night

Read the teach-first sections below before you run SQL or dbt. No assumed jargon — watermark, materialization, and each file are explained in plain English.

Business problem Meridian’s transaction history grows daily. Jordan’s nightly full refresh of the fact table burns warehouse credits and still misses same-day updates. Marcus: “Fix the ledger without doubling our Snowflake bill.”
Solution you will build Land Day-1 rows in LANDING.TXN_EVENTS, clean them in a dbt view stg_orders, then keep a durable fact table fct_orders_incremental up to date with incremental merge (only new/changed rows, keyed by txn id, filtered by an updated_at watermark).

What is a watermark? (assume you never heard the word)

Bookmark metaphor

Imagine a book of every transaction ever. Last night you finished reading up to page “2026-10-01 14:00” — that page number is your watermark (also called a high-water mark).

Tonight you do not re-read the whole book. You open at the bookmark and only process pages with a timestamp newer than that mark. When you’re done, the bookmark moves forward.

In our model the bookmark column is updated_at. On an incremental run dbt asks: “What is the MAX(updated_at) already in the fact table?” then only pulls staging rows where updated_at is greater than that.

After Day 1 run

Fact has rows 1001–1005.

Watermark = max(updated_at) = 2026-10-01 14:00

Day 2 source changes

New rows 1006, 1007 (Oct 2).

Row 1001 status → SETTLED with updated_at bumped to Oct 2.

Second dbt run

Only rows with updated_at > watermark enter the MERGE.

Old rows 1002–1005 are not rebuilt.

Classic bug If Jordan changes STATUS but forgets to bump UPDATED_AT, the watermark filter skips that row and Alex’s fact stays wrong. The timestamp is part of the contract with the source.

dbt “materialized” — what options exist, why we chose incremental

materialized=… tells dbt how to store the result of a model’s SELECT in Snowflake. It is not a Snowflake keyword — it is a dbt config that compiles to CREATE VIEW / CREATE TABLE / MERGE, etc.

materializedWhat Snowflake getsWhen Elena picks it
view CREATE VIEW — no stored copy; query always hits upstream Lightweight cleanup (stg_orders). Cheap, always fresh.
table CREATE TABLE AS SELECT — full rebuild every run Small dims, or when “always rebuild” is OK. Bad for huge growing facts.
incremental First run: build table. Later runs: only new/changed rows (MERGE here) Our choice for the txn fact — history is large; only deltas matter.
ephemeral No object — CTE inlined into downstream SQL Tiny helpers you never query alone (not used in this lab).
materialized_view Snowflake MV (adapter/support dependent) Advanced; Lab 05 talks Dynamic Tables as the Snowflake-native cousin.

Why incremental + merge for Meridian: Marcus won’t pay for rewriting millions of settled txns every night. unique_key='order_id' means “if txn 1001 already exists, UPDATE it; else INSERT.” That upsert is Snowflake MERGE — not a blind append (append alone would duplicate 1001).

Walk the code — line by line

A) stg_orders.sql — the translator

{{ source('landing', 'txn_events') }} means: “read the table declared in _sources.yml as Meridian’s landing dock.” dbt does not create TXN_EVENTS — you did, in SQL.

Renames (txn_id → order_id) keep bank language at the dock and slightly more “analytics” names in curated models. Still the same five rows.

select
    txn_id as order_id,
    client_id as customer_id,
    status,
    amount as order_total,
    updated_at
from {{ source('landing', 'txn_events') }}

B) fct_orders_incremental.sql — the ledger keeper

PiecePlain English
materialized='incremental'Don’t full-rebuild after the first run
unique_key='order_id'One row per txn; updates overwrite that id
incremental_strategy='merge'Compile to Snowflake MERGE (upsert)
{{ ref('stg_orders') }}Read the staging view (never skip staging)
is_incremental()False on first build; true on later runs
where updated_at > (select max… from {{ this }})Watermark filter — only rows newer than the fact’s current max timestamp
{{ this }}This model’s own table (the fact we’re updating)
dbt · fct_orders_incremental.sql
{{
  config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
  )
}}

select
    order_id,
    customer_id,
    status,
    order_total,
    updated_at
from {{ ref('stg_orders') }}

{% if is_incremental() %}
  where updated_at > (
    select coalesce(max(updated_at), '1900-01-01'::timestamp_ntz)
    from {{ this }}
  )
{% endif %}

Day 1 — create the main table at the dock

TXN_EVENTS is the source of truth

dbt will not create this. Run this SQL in Snowsight first. Every later model is a lens on this table.

SQL · sql/02_orders_source.sql
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA LANDING;

CREATE OR REPLACE TABLE TXN_EVENTS (
  TXN_ID       NUMBER,
  CLIENT_ID    NUMBER,
  STATUS       STRING,
  AMOUNT       NUMBER(12,2),
  UPDATED_AT   TIMESTAMP_NTZ
);

INSERT INTO TXN_EVENTS VALUES
  (1001, 1, 'POSTED',    40.00, '2026-10-01 10:00:00'),
  (1002, 2, 'POSTED',    15.50, '2026-10-01 11:00:00'),
  (1003, 3, 'SETTLED',   99.00, '2026-10-01 12:00:00'),
  (1004, 4, 'POSTED',    22.00, '2026-10-01 13:00:00'),
  (1005, 5, 'REVERSED',  10.00, '2026-10-01 14:00:00');

SELECT 'day1' AS batch, COUNT(*) AS n FROM TXN_EVENTS;
✓ n = 5 in LANDING.TXN_EVENTS

4

Day 2 — change the source, then prove the watermark

This is the whole point of the lab

Two inserts + one update with a newer UPDATED_AT. Second run MERGEs only those rows — history is not rebuilt.

SQL · sql/02_orders_day2.sql
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA LANDING;

INSERT INTO TXN_EVENTS VALUES
  (1006, 1, 'POSTED', 55.00, '2026-10-02 09:00:00'),
  (1007, 2, 'POSTED', 18.00, '2026-10-02 09:30:00');

UPDATE TXN_EVENTS
SET STATUS = 'SETTLED', UPDATED_AT = '2026-10-02 10:00:00'
WHERE TXN_ID = 1001;

SELECT TXN_ID, STATUS, UPDATED_AT FROM TXN_EVENTS ORDER BY TXN_ID;
Terminal · second run
dbt run --select fct_orders_incremental
SQL · prove merge
SELECT ORDER_ID, STATUS, UPDATED_AT
FROM CURATED.FCT_ORDERS_INCREMENTAL ORDER BY ORDER_ID;
  • 7 rows total (no duplicates on 1001)
  • 1001 is SETTLED
  • 1006 and 1007 exist
Elena’s wrap-up (say this out loud)
“Meridian’s problem was a nightly full refresh on growing txn history. The main table is LANDING.TXN_EVENTS. stg_orders is a view that renames columns; fct_orders_incremental is an incremental table that MERGEs on order_id and only reads rows newer than the updated_at watermark — a bookmark on the last processed timestamp. Day 2 inserts and a status change on 1001 merged without rebuilding the whole ledger. Outcome: cheaper pipeline, correct upserts, proof as MERGE not a full-table rewrite.”
