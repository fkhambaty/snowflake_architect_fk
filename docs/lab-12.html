Sources — boundary with RAW

Understand this before you copy

Sources document “we don’t own this table.” Lineage starts at {{ source('raw', 'orders_events') }}. Freshness blocks can alert when loads stall.

Interview: “Staging reads sources; marts read refs — never skip the source layer in enterprise repos.”
YAML · sources excerpt
version: 2

sources:
  - name: raw
    database: ARCH_INTERVIEW
    schema: RAW
    tables:
      - name: orders_events
        description: "Lab 02 source events for incremental merge demo"
        loaded_at_field: updated_at
        freshness:
          warn_after: {count: 24, period: hour}
          error_after: {count: 48, period: hour}

Model contract on a mart

Downstream tools (BI, other teams) get a stable column guarantee.

Understand this before you copy

Contract piecePlain English
contract: {enforced: true}dbt fails the build if model SQL output doesn’t match YAML columns/types
Column list with data_typeDocument + enforce schema for consumers
Architects use contracts on published marts — not every staging view.
YAML · contract example for fct_orders_incremental
version: 2

models:
  - name: fct_orders_incremental
    description: "Incremental order fact — published mart with enforced contract"
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: number
        tests: [unique, not_null]
      - name: customer_id
        data_type: number
      - name: status
        data_type: varchar
      - name: order_total
        data_type: number
      - name: updated_at
        data_type: timestamp_ntz
        tests: [not_null]

Incremental model (reference SQL)

Understand this before you copy

Snowflake merge strategy with unique_key — same as Lab 02. Contract YAML must match this SELECT list.

SQL · fct_orders_incremental.sql core
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
) }}

select
    order_id,
    customer_id,
    status,
    order_total,
    updated_at
from {{ ref('stg_orders') }}

{% if is_incremental() %}
  where updated_at > (select coalesce(max(updated_at), '1900-01-01'::timestamp_ntz) from {{ this }})
{% endif %}
4

Slim CI talktrack

Full dbt build on every PR doesn’t scale. Slim CI builds the modified subgraph.

Understand this before you copy

  1. On merge to main, upload manifest.json artifact from prod-like target.
  2. On PR, download that manifest → --state path/to/prod/
  3. dbt ls --select state:modified+ --resource-type model — what changed + downstream
  4. dbt build --select state:modified+ --defer --state … — run only that slice, defer unmodified refs to prod
Interview line: “Slim CI cuts warehouse spend and queue time; contracts stop breaking BI when a column rename slips in.”
Shell · Slim CI commands (illustration)
dbt deps
dbt ls --select state:modified+ --resource-type model --state ./prod_artifact/
dbt build --select state:modified+ --defer --state ./prod_artifact/
5

GitHub Actions sketch (illustration only)

Understand this before you copy

Wire secrets for Snowflake + store prod manifest from scheduled main-branch job. PR job uses same pattern with pull_request trigger. Adjust paths to your repo.

YAML · .github/workflows/dbt-slim-ci.yml (sample)
name: dbt Slim CI
on:
  pull_request:
    paths: ['dbt_project/**']

jobs:
  slim-ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: pip install dbt-snowflake
      - name: Download prod manifest artifact
        uses: actions/download-artifact@v4
        with:
          name: dbt-manifest-prod
          path: prod_artifact/
      - name: Slim build
        env:
          SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
          SNOWFLAKE_USER: ${{ secrets.SNOWFLAKE_USER }}
          SNOWFLAKE_PASSWORD: ${{ secrets.SNOWFLAKE_PASSWORD }}
        working-directory: dbt_project
        run: |
          dbt deps --profiles-dir .
          dbt build --select state:modified+ --defer --state ../prod_artifact/ --profiles-dir .

Quick self-check

  1. Source vs ref — when use each?
  2. What breaks first if a mart SQL adds a column not in the contract?
  3. What does state:modified+ include?
Click for short answers
  1. Source for upstream RAW/external; ref for models you own in the DAG.
  2. dbt build fails contract enforcement (if enforced: true).
  3. Changed nodes plus all downstream dependents.
60-second interview answer
“I treat RAW as dbt sources with freshness, stage in views, publish marts with enforced contracts. CI uses Slim — state:modified+ with defer to prod manifest — so PRs only rebuild the affected subgraph. On Snowflake I keep incremental merge on facts with explicit unique keys and test order_id in YAML.”
