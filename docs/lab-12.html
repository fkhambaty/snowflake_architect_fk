The contract YAML (already in the repo)

Step 1 · coach

What is a contract?

What this is

A written promise: these five columns, these types. Open dbt_project/models/marts/schema.yml — you should already see contract.enforced: true.

YAML · models/marts/schema.yml (the promise)
models:
  - name: fct_orders_incremental
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: number
        tests: [unique, not_null]
      - name: customer_id
        data_type: number
      - name: status
        data_type: varchar
      - name: order_total
        data_type: number
      - name: updated_at
        data_type: timestamp_ntz
        tests: [not_null]
✓ Promise written — next step wires incremental so dbt accepts the contract
2

Fix incremental + contract (the error you hit)

Step 2 · coach

Why on_schema_change = fail?

Why dbt yelled

On dbt 1.x+, an incremental model with a contract cannot use on_schema_change: ignore. It must be fail or append_new_columns. We want fail — silent new columns are how Alex’s tile dies.

SQL/Jinja · fct_orders_incremental.sql config
{{
  config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge',
    on_schema_change='fail',
    schema='SILVER_CURATED'
  )
}}
Pull latest git if your file still lacks on_schema_change='fail' — that was the Lab 12 bug.
✓ Seatbelt wired — ignore is gone

Bonus — save a “prod map” for Slim CI

Step 4 · coach

Save yesterday’s map

Why

Slim CI compares your PR graph to yesterday’s prod graph (manifest.json). No map → state:modified+ has nothing to compare. Skip Steps 4–5 if you only care about contracts today.

About dbt deps

Our packages.yml is empty — “No packages were found” is normal, not an error. You can skip dbt deps.

Shell · pretend today’s target is prod
cd dbt_project
dbt run --select stg_orders fct_orders_incremental
mkdir prod_artifact 2>$null
copy target\manifest.json prod_artifact\manifest.json
✓ prod_artifact/manifest.json exists
5

Bonus — Slim CI list + build

Step 5 · coach

Slim CI in one breath

In one breath

state:modified+ = models you changed + anything that depends on them. --defer = reuse unchanged parents from the prod map instead of rebuilding the world.

Shell · list then build
cd dbt_project
dbt ls --select state:modified+ --resource-type model --state ./prod_artifact/
dbt build --select state:modified+ --defer --state ./prod_artifact/
If nothing is “modified,” tweak a comment in stg_orders.sql, save, then re-run the two commands — you should see staging + the fact.

Interviewer presses further — say these out loud

Cover each answer before you open it.

Q1. Why contract the fact, not every staging model?

Say: Staging is an internal translator. The fact is Alex/Looker’s API. Contract the published boundary — contracting every stg_ slows the team without protecting the board.

Q2. Why on_schema_change = fail with contracts?

Say: Incremental + contract can’t ignore schema drift. fail stops the PR; append_new_columns is the other legal option when you intentionally add columns. ignore is invalid and unsafe for Alex.

Q3. What still breaks Alex even with a green contract?

Say: Same name/type, wrong meaning — or watermark stops updating. Contracts catch schema breaks; tests and ownership catch semantic breaks.

Q4. Slim CI with a stale prod manifest — what goes wrong?

Say: You under-build or defer to a ghost graph — green CI, red prod. Manifest freshness is part of the pipeline, not optional.

Q5. When do you refuse Slim CI?

Say: Cross-cutting macro changes or release trains where modified+ is known-blind. Slim CI is PR cost control; releases can still full-build critical marts.

Outcome: board tiles stay stable; Jordan still ships without rebuilding Meridian every PR.”
