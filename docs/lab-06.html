Lab 06 · Thursday night · You are Elena · Jordan’s overnight files

Files arrive overnight — automate the dock

Read every Teach first section before you run SQL. You will build the same pattern Jordan needs for partner CSV drops: stage → file format → COPY INTO → LANDING. Snowpipe is the story of automated COPY — this lab does not walk fake AWS wiring.

Business problem Morning desk finds CSV drops with no loader. Jordan begs for a repeatable pattern before Nora’s partner feed scales up. Sam wants an audit trail: who loaded what, when.
Solution you will build Internal stage in schema FILE_IN, a CSV file format, manual COPY INTO LANDING.TXN_LANDING. In production Elena would attach Snowpipe — same COPY semantics, triggered when files land on the stage.

Teach first — dictionary (no assumed knowledge)

WordLayman meaningBank metaphor
Stage A named “parking lot” where files sit before Snowflake loads them into a table Truck bay at the back of the bank — pallets aren’t on the ledger shelf yet
Internal stage Storage inside Snowflake’s account (starts with @ in SQL) Bank-owned bay — no external cloud bucket required for this lab
File format Reusable rules: CSV vs JSON, headers, quote character, etc. The spec sheet: “these pallets are comma-separated with quotes”
COPY INTO (table) Snowflake command: read files from a stage and insert rows into a table Forklift from bay → official LANDING shelf
COPY INTO (stage) Upload or create a file on the stage (we simulate a partner file in-lab) Backing a truck into the bay with today’s CSV
LANDING.TXN_LANDING Physical table for file-sourced txns (separate from Jordan’s TXN_EVENTS stream path) Receiving dock ledger — raw rows from files before curation
Snowpipe Serverless auto-loader: when a new file hits the stage, Snowflake runs the same COPY pipeline Bay sensor + automatic forklift — not a different load language
ON_ERROR = 'ABORT_STATEMENT' If one row is bad, stop the whole load (fail loud, don’t silently skip) Reject the whole pallet if the manifest doesn’t match

The whole flow in one picture

Four objects. Files never jump straight into LANDING — they pause on the stage first.

1 · File txn_day1.csv.gz Partner drop (simulated in lab)
2 · Stage @STG_TXN_INTERNAL FILE_IN schema · uses FF_CSV_SIMPLE
3 · Loader COPY INTO table Parse CSV → typed columns
4 · Table LANDING.TXN_LANDING Queryable rows for downstream jobs

Snowpipe (interview one-liner): “We’d define a pipe with the same stage, file format, and target table. Snowflake watches the stage and runs COPY when files arrive — Jordan doesn’t click Run at 3 a.m.”

Thursday night · loading dock

Jordan: “Can we stop drag-and-drop in Snowsight?” Elena: “Stage is the bay, file format is how we read commas, COPY is the loader. Snowpipe is COPY on autopilot — I’ll prove the manual path first so Sam can audit loads in history.”

1

Set session + open FILE_IN

What this does

Elena’s lab badge, cheap warehouse, bank database. FILE_IN is the schema where inbound file objects live (stage + format).

Why Elena does it

Keeps file plumbing separate from LANDING tables Jordan already owns.

SQL · context
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
CREATE SCHEMA IF NOT EXISTS FILE_IN;
USE SCHEMA FILE_IN;
✓ Snowsight shows schema FILE_IN under MERIDIAN_BANK
2

Define how to read CSV

What this does

Creates FF_CSV_SIMPLE: CSV type, optional double-quote wrapping, no header row in our tiny lab file.

SQL · file format
CREATE OR REPLACE FILE FORMAT FF_CSV_SIMPLE
  TYPE = CSV
  FIELD_OPTIONALLY_ENCLOSED_BY = '"'
  SKIP_HEADER = 0;
✓ Database → FILE_IN → File Formats → FF_CSV_SIMPLE
3

Create the internal stage

What this does

STG_TXN_INTERNAL defaults to the file format above so every file in the bay parses the same way.

SQL · stage
CREATE OR REPLACE STAGE STG_TXN_INTERNAL
  FILE_FORMAT = FF_CSV_SIMPLE;
✓ Stages list shows STG_TXN_INTERNAL (internal, not S3 URL)
4

Create the landing table

What this does

Target table with typed columns — COPY will map file fields into these slots.

SQL · LANDING.TXN_LANDING
CREATE OR REPLACE TABLE LANDING.TXN_LANDING (
  TXN_ID NUMBER,
  CLIENT_ID NUMBER,
  STATUS STRING,
  AMOUNT NUMBER(12,2)
);
✓ Empty table LANDING.TXN_LANDING — 0 rows until COPY
5

Park a “partner file” on the stage

What this does

In production Jordan would PUT a file from a laptop or sync from cloud storage. Here we COPY INTO @stage/… from inline VALUES — same result: a gzip CSV named txn_day1.csv.gz on the stage.

SQL · simulate file on stage
COPY INTO @STG_TXN_INTERNAL/txn_day1.csv.gz FROM (
  SELECT * FROM VALUES
    (2001, 1, 'POSTED', 10.00),
    (2002, 2, 'POSTED', 20.00),
    (2003, 3, 'SETTLED', 30.00)
) OVERWRITE = TRUE SINGLE = TRUE;
✓ LIST @STG_TXN_INTERNAL; shows txn_day1.csv.gz
6

COPY from stage into LANDING

What this does

Reads matching files from the stage, parses with FF_CSV_SIMPLE, inserts into TXN_LANDING. PATTERN picks our file; ON_ERROR = 'ABORT_STATEMENT' fails the load if parsing breaks.

What you should see

COPY result columns: file name, rows loaded, errors (0).

SQL · load into table
COPY INTO LANDING.TXN_LANDING
FROM @STG_TXN_INTERNAL
FILE_FORMAT = (FORMAT_NAME = 'FILE_IN.FF_CSV_SIMPLE')
PATTERN = '.*txn_day1.csv.gz'
ON_ERROR = 'ABORT_STATEMENT';
✓ Status LOADED · 3 rows parsed
7

Verify + interview close

What you should see

Three txn ids 2001–2003 with amounts 10, 20, 30. Sam can later use load history / query history for audit.

SQL · proof
SELECT * FROM LANDING.TXN_LANDING ORDER BY TXN_ID;
SELECT 'Lab 06 landing COPY OK' AS status;
✓ n = 3 · status row confirms lab script parity with sql/06_landing_copy.sql
