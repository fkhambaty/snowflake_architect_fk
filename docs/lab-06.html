File format + internal stage

Understand this before you copy

ObjectPlain English
FILE FORMAT FF_CSV_SIMPLERules for reading CSV (quotes, headers)
STAGE STG_ORDERS_INTERNALFolder inside Snowflake to hold files
INTERNAL stageNo cloud bucket — perfect for learning COPY mechanics
Snowpipe on external stages triggers COPY when new files appear — same load semantics, different trigger.
SQL · format + stage
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;

CREATE SCHEMA IF NOT EXISTS STAGE_DATA;
USE SCHEMA STAGE_DATA;

CREATE OR REPLACE FILE FORMAT FF_CSV_SIMPLE
  TYPE = CSV
  FIELD_OPTIONALLY_ENCLOSED_BY = '"'
  SKIP_HEADER = 0;

CREATE OR REPLACE STAGE STG_ORDERS_INTERNAL
  FILE_FORMAT = FF_CSV_SIMPLE;

Simulate “file landed” — COPY into stage

Understand this before you copy

Real life: an app drops orders_day1.csv into S3. Here we COPY INTO @stage from inline VALUES to create that file.

OptionMeaning
OVERWRITE = TRUEReplace same path on re-run
SINGLE = TRUEOne output file (.csv.gz)
After this step, LIST @stage should show the gzipped CSV.
SQL · write file to stage
COPY INTO @STG_ORDERS_INTERNAL/orders_day1.csv.gz
FROM (
  SELECT * FROM VALUES
    (2001, 1, 'CREATED', 10.00),
    (2002, 2, 'CREATED', 20.00),
    (2003, 3, 'SHIPPED', 30.00)
)
OVERWRITE = TRUE
SINGLE = TRUE;

LIST @STG_ORDERS_INTERNAL;
✓ See orders_day1.csv.gz in LIST output

COPY INTO landing table (what Snowpipe automates)

Understand this before you copy

SQLPlain English
COPY INTO RAW.ORDERS_LANDING FROM @stageLoad staged files into the table
PATTERN = '.*orders_day1.csv.gz'Only pick matching files
ON_ERROR = 'ABORT_STATEMENT'Fail fast if a row is bad

Snowpipe = event-driven service that runs COPY (or similar load) when new files land on an external stage. You still define file format, target table, and error policy.

Interview: “I design idempotent loads, file patterns, and landing→raw promotion — Snowpipe handles the trigger.”
SQL · load landing
COPY INTO RAW.ORDERS_LANDING
FROM @STG_ORDERS_INTERNAL
FILE_FORMAT = (FORMAT_NAME = 'STAGE_DATA.FF_CSV_SIMPLE')
PATTERN = '.*orders_day1.csv.gz'
ON_ERROR = 'ABORT_STATEMENT';

SELECT * FROM RAW.ORDERS_LANDING ORDER BY ORDER_ID;

SELECT 'Lab 06 landing COPY OK' AS status;
✓ Three rows: 2001, 2002, 2003

Snowpipe vs manual COPY (talktrack)

No extra SQL required — read for the interview

  • Manual COPY (this lab): you run COPY when you know the file is ready.
  • Snowpipe: cloud storage notification → Snowflake queues loads → COPY-like ingest continuously.
  • Cost angle: Snowpipe charges per file/batch; warehouses may still participate depending on pipe setup (mention auto-ingest vs REST).
You don’t need AWS keys in this course — explain the pattern confidently from internal stage experience.
✓

Self-check

  1. Stage vs table — what lives where?
  2. Why a landing table instead of loading straight into a mart?
  3. What does Snowpipe add on top of COPY?
  4. What does ON_ERROR = 'ABORT_STATEMENT' protect?
Click for short answers
  1. Stage holds files; table holds relational rows after load.
  2. Isolate raw file shape, replay loads, and apply RBAC/transforms downstream.
  3. Automatic, event-driven ingestion when files arrive — not manual COPY runs.
  4. Prevents partial silent bad data — whole statement fails.
Interview soundbite
“Landing zone pattern: files hit a stage, COPY INTO a RAW landing table with explicit file format and pattern, then promote through medallion layers. Snowpipe is automated COPY on external stages with queueing and notifications — I still own schema evolution, dedupe, and error handling.”
