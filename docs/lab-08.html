Lab 08 · Friday noon · You are Elena

Stop scanning a year when Alex wants 7 days

Huge event history makes ‘last 7 days’ expensive. Elena clusters CURATED.BIG_EVENTS on EVENT_DATE.

Business problem Risk team filters BIG_EVENTS to recent weeks; queries scan hundreds of thousands of micro-partitions. Finance sees the credit line move.
Solution you will build Synthetic big table, inspect SYSTEM$CLUSTERING_INFORMATION, CLUSTER BY (EVENT_DATE), re-run filtered aggregate.

Clustering demo

SQL · sql/08_clustering.sql
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA CURATED;

CREATE OR REPLACE TABLE BIG_EVENTS AS
SELECT SEQ4() AS EVENT_ID, UNIFORM(1, 5, RANDOM()) AS CLIENT_ID,
  DATEADD('day', -UNIFORM(0, 364, RANDOM()), CURRENT_DATE()) AS EVENT_DATE,
  UNIFORM(1, 100, RANDOM()) / 1 AS AMOUNT
FROM TABLE(GENERATOR(ROWCOUNT => 200000));

SELECT SYSTEM$CLUSTERING_INFORMATION('CURATED.BIG_EVENTS', '(EVENT_DATE)');
ALTER TABLE BIG_EVENTS CLUSTER BY (EVENT_DATE);
SELECT COUNT(*), SUM(AMOUNT) FROM BIG_EVENTS
WHERE EVENT_DATE >= DATEADD('day', -7, CURRENT_DATE());
SELECT 'Lab 08 clustering demo ready' AS status;

Search optimization is for point lookups on IDs — Elena mentions it in interviews; clustering fits date-filtered risk reports.

Elena’s wrap-up (say this out loud)
“Meridian’s last-7-days reports were scanning the whole year. I clustered CURATED.BIG_EVENTS on EVENT_DATE and validated overlap with SYSTEM$CLUSTERING_INFORMATION. Outcome: fewer bytes scanned on date filters — better speed and FinOps story for Marcus.”
