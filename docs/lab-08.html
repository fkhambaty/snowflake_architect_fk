Lab 08 · Friday noon · You are Elena · Risk dashboards

Stop scanning a year when Alex wants 7 days

Read Teach first before you build BIG_EVENTS. Risk filters on recent dates; without clustering Snowflake may read huge swaths of history. You will cluster on EVENT_DATE and re-run the last-7-days aggregate.

Business problem Risk team filters BIG_EVENTS to recent weeks; at production scale queries scan hundreds of thousands of micro-partitions. Finance sees the credit line move when every “last 7 days” report reads a year of junk.
Solution you will build Synthetic 200k-row table, read SYSTEM$CLUSTERING_INFORMATION, run ALTER TABLE … CLUSTER BY (EVENT_DATE), then prove the same filtered aggregate (Profile in Lab 07 vocabulary: better pruning on real volume).

Teach first — layman picture

Library metaphor

Imagine a year of risk events thrown into one pile (random dates). Alex asks for “books from the last 7 days.” A librarian must flip through every book to check dates — that’s a full micro-partition scan.

Clustering is the librarian re-shelving: keep nearby dates on nearby shelves inside the table. Snowflake still stores micro-partitions automatically, but a clustering key (EVENT_DATE here) tells the service to co-locate similar values so pruning skips irrelevant shelves.

WordLayman meaningNot the same as…
Micro-partition Automatic storage slice inside a table (Snowflake-managed) Manual Hive partitions you name in path
Clustering key Column(s) Snowflake tries to sort/co-locate over time (CLUSTER BY) Primary key — uniqueness vs scan efficiency
Pruning Skip micro-partitions whose min/max metadata proves they can’t match your filter Deleting rows — data still there, just unread
SYSTEM$CLUSTERING_INFORMATION Health report: how “well sorted” the table is on the clustering key Query Profile — this is table maintenance metrics
Search optimization Snowflake feature for point lookups on high-cardinality IDs Date-range reports — Elena mentions it in interviews; clustering fits risk date filters

2

Create BIG_EVENTS (synthetic history)

What this does

200k rows with random dates across ~365 days — mimics messy event history at lab scale.

What you should see

Table CURATED.BIG_EVENTS with columns EVENT_ID, CLIENT_ID, EVENT_DATE, AMOUNT.

SQL · generate rows
CREATE OR REPLACE TABLE BIG_EVENTS AS
SELECT
  SEQ4() AS EVENT_ID,
  UNIFORM(1, 5, RANDOM()) AS CLIENT_ID,
  DATEADD('day', -UNIFORM(0, 364, RANDOM()), CURRENT_DATE()) AS EVENT_DATE,
  UNIFORM(1, 100, RANDOM()) / 1 AS AMOUNT
FROM TABLE(GENERATOR(ROWCOUNT => 200000));
✓ ~200k rows — date column spans roughly a year
3

Read clustering health (before)

What this does

Asks Snowflake how well rows align on EVENT_DATE before we declare a clustering key.

What you should see

JSON-ish stats — overlap / depth numbers. Interview: “I’d track this after loads; re-cluster if overlap drifts.”

SQL · clustering information
SELECT SYSTEM$CLUSTERING_INFORMATION(
  'CURATED.BIG_EVENTS', '(EVENT_DATE)'
);
4

Declare the clustering key

What this does

ALTER TABLE … CLUSTER BY (EVENT_DATE) tells Snowflake to maintain better date locality over time (automatic background work).

SQL · cluster key
ALTER TABLE BIG_EVENTS CLUSTER BY (EVENT_DATE);
✓ Table DDL shows clustering key EVENT_DATE in Snowsight
5

Run Alex’s “last 7 days” aggregate

What this does

Same business filter Risk runs daily — count and sum only recent events.

What you should see

One result row (count + sum). On tiny lab WH it’s fast either way; tie back to Lab 07 Profile for bytes/pruning at scale.

SQL · filtered aggregate
SELECT COUNT(*), SUM(AMOUNT)
FROM BIG_EVENTS
WHERE EVENT_DATE >= DATEADD('day', -7, CURRENT_DATE());

“Meridian’s last-7-days reports were scanning too much history because dates were scattered across micro-partitions. Search optimization is for ID point lookups; clustering fits our date-window risk pattern. Outcome: fewer bytes scanned at scale — better speed and FinOps story for Marcus.”
