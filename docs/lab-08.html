Lab 08 · Performance · Understand first, then run

Clustering keys & search optimization

Snowflake stores data in micro-partitions. A clustering key helps the engine skip partitions when your filters match. Read each blue box → copy the SQL under it.

After this lab you can explain
  • What SYSTEM$CLUSTERING_INFORMATION tells you (and a sample cert-style answer)
  • When to add CLUSTER BY vs leave natural load order
  • When search optimization beats clustering (point lookups, cost tradeoff)
  • How to prove pruning in the Query Profile
Prerequisites Lab 00 (ARCH_INTERVIEW, warehouse WH_ARCH_XS, role ROLE_ARCH_LAB_ADMIN).

Big picture (30 seconds)

Large table
→
Filter on key column
e.g. EVENT_DATE
→
Prune micro-partitions
→
Less bytes scanned

Clustering is not an index in the Oracle sense. Snowflake rewrites micro-partitions over time (automatic clustering) when you define a key. You still pay for maintenance credits.

1

Build a demo table big enough to see pruning

200k rows is tiny for production — but enough on a trial to open Query Profile.

Understand this before you copy

SQL ideaPlain English
GENERATOR(ROWCOUNT => …)Fake rows without a CSV file
EVENT_DATE spread over 365 daysFilters on “last 7 days” should skip old partitions — once clustered
CURATED.BIG_EVENTSLab table; safe to drop later
Interviewers care: you chose a key that matches real query patterns, not every column.
SQL · Step 1 · create BIG_EVENTS
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA CURATED;

CREATE OR REPLACE TABLE BIG_EVENTS AS
SELECT
  SEQ4() AS EVENT_ID,
  UNIFORM(1, 5, RANDOM()) AS CUSTOMER_ID,
  DATEADD('day', -UNIFORM(0, 364, RANDOM()), CURRENT_DATE()) AS EVENT_DATE,
  UNIFORM(1, 100, RANDOM()) / 1 AS AMOUNT
FROM TABLE(GENERATOR(ROWCOUNT => 200000));
✓ Table created — note row count in results.
2

Baseline: clustering information before a key

This is the function cert exams love to ask about.

Understand this before you copy

SYSTEM$CLUSTERING_INFORMATION('schema.table', '(COL)') returns JSON stats. Focus on average_overlap_ratio and average_depth.

Metric (typical)What to say in an interview / sample exam
average_overlap_ratioHow much partition ranges overlap on that key — lower is better for pruning
average_depthHow deep clustering runs — very high depth can mean the key fights the load pattern
No key yetStats still describe natural layout; compare after CLUSTER BY
Sample exam soundbite: “I use SYSTEM$CLUSTERING_INFORMATION to see overlap on the declared key; if overlap stays high after automatic clustering, I revisit the key or query patterns.”
SQL · Step 2 · baseline clustering info
SELECT SYSTEM$CLUSTERING_INFORMATION('CURATED.BIG_EVENTS', '(EVENT_DATE)');
3

Declare a clustering key

Automatic clustering runs asynchronously — re-check info after a few minutes if stats look unchanged.

Understand this before you copy

SQLPlain English
ALTER TABLE … CLUSTER BY (EVENT_DATE)Tell Snowflake: keep partitions ordered/grouped on this column
Automatic clusteringBackground job — not instant; costs credits on large tables
Architect rule: cluster on columns used in WHERE / joins that scan large history — often dates or tenant IDs.
SQL · Step 3 · add clustering key
ALTER TABLE BIG_EVENTS CLUSTER BY (EVENT_DATE);

SELECT SYSTEM$CLUSTERING_INFORMATION('CURATED.BIG_EVENTS', '(EVENT_DATE)');
4

Run a filter query & open Query Profile

Prove pruning with “partitions scanned” — not vibes.

Understand this before you copy

This query filters to the last 7 days. After clustering, Query Profile should show fewer partitions scanned than a full table scan.

In interviews: “I validate with Query Profile partition pruning, not only elapsed time.”
SQL · Step 4 · pruning-friendly query
SELECT COUNT(*), SUM(AMOUNT)
FROM BIG_EVENTS
WHERE EVENT_DATE >= DATEADD('day', -7, CURRENT_DATE());
✓ In Snowsight: History → this query → Query Profile → TableScan / partitions scanned.
5

Search optimization (talktrack — optional SQL)

Use when clustering does not help point lookups.

Understand this before you copy

Search optimization builds a search access path for equality / substring predicates (e.g. WHERE EVENT_ID = 12345) when micro-partition pruning alone is weak.

When to mention itTradeoff to say out loud
High-selectivity point lookups on a column not in the clustering keyExtra storage + background maintenance credits
Lookup by business key, ID, email tokenNot a replacement for clustering on time-range analytics
Interview line: “Clustering for range scans; search optimization for needle-in-haystack equality — I weigh scan savings vs SO maintenance cost.”
SQL · Step 5 · optional search optimization
-- Optional: only if you want to demo point lookup acceleration
ALTER TABLE BIG_EVENTS ADD SEARCH OPTIMIZATION ON EQUALITY(EVENT_ID);

SELECT EVENT_ID, AMOUNT
FROM BIG_EVENTS
WHERE EVENT_ID = 42;  -- pick an ID that exists or expect 0 rows
✓

Quick self-check

  1. What does a lower average_overlap_ratio imply?
  2. Why is clustering not the same as a traditional B-tree index?
  3. When would you propose search optimization instead of (or in addition to) clustering?
Click for short answers
  1. Better separation of partition bounds on the key → more pruning opportunity.
  2. Snowflake manages micro-partitions; clustering rewrites layout over time — no user-managed index pages.
  3. Equality / point lookups on columns that range filters don’t prune well — accept SO storage/maintenance cost.
60-second interview answer
“For large fact tables I align clustering keys with dominant filters — often event or load dates. I check SYSTEM$CLUSTERING_INFORMATION for overlap on that key and confirm pruning in Query Profile. For rare high-selectivity point lookups I consider search optimization and call out the extra maintenance cost. I don’t cluster every column — keys have a credit cost.”
