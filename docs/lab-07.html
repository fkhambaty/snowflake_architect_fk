Baseline — cheap filter query

What this does

Single-table filter on COUNTRY — should scan only client rows, fast profile baseline.

What you should see

Small result set (US clients from Lab 00). In Profile: modest bytes scanned vs the join in step 3.

SQL · filter only
SELECT * FROM BRONZE_LANDING.CLIENTS
WHERE COUNTRY = 'US';
✓ Only US rows — note runtime in Query History
3

Reproduce Alex’s board rollup (the heavy join)

What this does

Joins every client to every txn, groups by country — the pattern Alex runs before the meeting.

Why Elena runs it separately

So Query History shows two queries — easy to open Profile on the join, not the filter.

SQL · Alex board query
SELECT c.COUNTRY, COUNT(*) AS TXNS, SUM(t.AMOUNT) AS VOLUME
FROM BRONZE_LANDING.CLIENTS c
JOIN BRONZE_LANDING.TXN_EVENTS t ON t.CLIENT_ID = c.CLIENT_ID
GROUP BY c.COUNTRY
ORDER BY VOLUME DESC;
✓ One row per country with txn counts — this is the query you profile
4

Inspect warehouse headroom

What this does

SHOW WAREHOUSES lists size, state, and multi-cluster settings for WH_BANK_XS.

What you should see

Size column = XS (or your lab default). Interview: “I’d bump size temporarily for the board window only after SQL/scan fixes.”

SQL · warehouse metadata
SHOW WAREHOUSES LIKE 'WH_BANK_XS';
5

Open Query Profile (UI step)

What this does

Not SQL — Snowsight navigation after step 3 completes.

Elena narrates in the profile

  • TableScan nodes — bytes scanned on CLIENTS vs TXN_EVENTS
  • Join — build/probe side, row counts (lab data is tiny; vocabulary matters in interview)
  • Partition pruning — if present and low on real big tables, clustering next
  • Remote disk spill — if any, call out upsize or rewrite
  • Warehouse load — queue time vs execution time
SQL · reminder row
SELECT 'Open Query History → JOIN query → Query Profile' AS next_step;
✓ You can explain bytes scanned vs warehouse size without guessing
