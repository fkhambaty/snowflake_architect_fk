Lab 07 · Performance · Understand first, then run

Query Profile + warehouse scale up vs scale out

Run a light query and a heavier join. Then open Query Profile in Snowsight and narrate what you see. Architects tune SQL shape first — then warehouse size and concurrency.

Prerequisites RAW.CUSTOMERS (Lab 00) and RAW.ORDERS_EVENTS (Lab 02 Day-1).

Big picture

Scale up = bigger warehouse (more power per query). Scale out = more warehouses or clusters handling more queries at once — not one query magically using infinite CPUs unless multi-cluster (Enterprise+).

2

Run join + aggregate (profile this one)

Understand this before you copy

This query touches two tables, joins on CUSTOMER_ID, then groups by country.

Step in planWhat to say in interview
TableScanReading micro-partitions from each table
JoinHow rows match — hash join common at scale
AggregateGROUP BY reduces rows to country totals
Run this query, then immediately open Query History — don’t lose the query id.
SQL · join + aggregate
SELECT
  c.COUNTRY,
  COUNT(*) AS ORDERS,
  SUM(o.ORDER_TOTAL) AS REVENUE
FROM RAW.CUSTOMERS c
JOIN RAW.ORDERS_EVENTS o
  ON o.CUSTOMER_ID = c.CUSTOMER_ID
GROUP BY c.COUNTRY
ORDER BY REVENUE DESC;
3

Open Query Profile in Snowsight (click path)

Understand this before you click

  1. Snowsight left nav → Monitoring → Query History
  2. Find the JOIN query you just ran (sort by start time)
  3. Click the query id or row to open details
  4. Open the Query Profile tab (execution plan + operator tree)
  5. Expand nodes: look for Join, Aggregate, bytes scanned, time spent
Interviewers want you to connect “slow step in profile” → “fix SQL or data layout or warehouse.”
What to narrate (even on 5-row data)
  • Which operator took the most time?
  • Did both tables scan fully? (At scale: pruning/clustering)
  • Would a pre-aggregated mart (Lab 04 gold) shrink work?
SQL · reminder
SELECT 'Lab 07: open Query History → click the JOIN query → Query Profile' AS next_step;

Inspect warehouse settings

Understand this before you copy

ConceptPlain English
Scale upALTER WAREHOUSE … SET WAREHOUSE_SIZE = 'SMALL' — more CPU/memory per warehouse
Scale outMore separate warehouses for different workloads, or multi-cluster for concurrent users
WH_ARCH_XSExtra-small — cheap for labs; heavy jobs need bigger size or better SQL
Auto-suspendStop billing when idle — architects set sensible timeouts
Bigger warehouse rarely fixes a cartesian join — fix the join first.
SQL · SHOW WAREHOUSES
SHOW WAREHOUSES LIKE 'WH_ARCH_XS';

In UI: Admin → Warehouses → WH_ARCH_XS → note size, auto-suspend, auto-resume.

✓

Self-check

  1. Scale up vs scale out — one line each?
  2. What tab in Snowsight shows operator-level time?
  3. Name one SQL change that beats resizing warehouse for a bad join.
  4. Why use a gold mart before ad-hoc country revenue queries?
Click for short answers
  1. Scale up = larger WH for more per-query power; scale out = more capacity/concurrency across workloads.
  2. Query Profile on the query detail page.
  3. Fix join keys/filter early, pre-aggregate, reduce columns scanned, cluster/prune large tables.
  4. Smaller scanned data, known grain, cheaper repeatable BI queries.
Interview soundbite
“I start with Query Profile to find dominant operators — scan, join, spill — then tune SQL and micro-partition pruning. I scale warehouse size when the plan is sound but needs more compute per query. I scale out with separate warehouses or multi-cluster when concurrency queues, not as a substitute for bad joins.”
