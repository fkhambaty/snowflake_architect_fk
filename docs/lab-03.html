Lab 03 · Wednesday AM · You are Elena · Sam vs Alex

Even clean tables still leak email

Read every Teach first box before you run SQL. Lab 01 locked the vault door. This lab puts rules on a glass window so the same table looks different for Alex vs Sam.

Business problem Alex can read curated clients — but he still sees full email addresses. Sam (Compliance) needs the real email for audits. Marcus refuses two copy-paste tables (“analyst_clients” vs “audit_clients”). Regulator: one table, different what-you-see by job.
Solution (plain English) Build one table CLIENTS_GOV. Hang two automatic rules on it: (1) blur email unless you’re Compliance, (2) hide whole rows for countries you’re not allowed to see. Same SELECT for Alex and Sam — Snowflake changes the answer.

Teach first — dictionary (no assumed knowledge)

WordLayman meaningBank metaphor
Policy A reusable rule Snowflake runs automatically when someone queries A posted bank regulation, not a handwritten sticky note
Masking policy Changes what a column looks like (still one row) Frosted glass on the email field — you see a row, not the real address
Row access policy (RAP) Hides entire rows you shouldn’t see Country drawers locked — CA/UK clients vanish for Alex

Masking Column disguise Email → ***@domain · row still there
Row access Row filter Whole client disappears if country not allowed

Build the one governed table

Why a copy from LANDING?

Landing stays raw for Jordan. CLIENTS_GOV is the shelf we hang rules on for consumers. (In production you might use a secure view — table is clearer for learning.)

SQL · CLIENTS_GOV
CREATE OR REPLACE TABLE CURATED.CLIENTS_GOV AS
SELECT CLIENT_ID, FULL_NAME, EMAIL, PHONE, COUNTRY, SSN_LAST4, CREATED_AT
FROM LANDING.CLIENTS;
✓ Same 5 clients as Lab 00 — policies not attached yet
3

Write the email “frosted glass” rule

Read the CASE like English

“When the active badge is Compliance or Lab Admin → show the real email. Otherwise → replace everything before @ with ***.”

AS (val STRING) RETURNS STRING = this rule takes one email string in, returns one string out.

SQL · masking policy
USE SCHEMA RISK_CTRL;

CREATE OR REPLACE MASKING POLICY MP_EMAIL_MASK AS (val STRING)
  RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('FR_COMPLIANCE', 'ROLE_BANK_LAB_ADMIN') THEN val
    ELSE REGEXP_REPLACE(val, '.+@', '***@')
  END;
✓ Policy object exists — not yet stuck on the EMAIL column
4

Country permission list (entitlements)

Why a table?

Hard-coding countries inside the policy is brittle. A small table is the “who may see which country” checklist. Alex → US only. Sam → US, CA, UK.

SQL · entitlement table
CREATE OR REPLACE TABLE RISK_CTRL.RAP_COUNTRY_ENTITLEMENT (
  ROLE_NAME STRING,
  COUNTRY   STRING
);

DELETE FROM RISK_CTRL.RAP_COUNTRY_ENTITLEMENT;

INSERT INTO RISK_CTRL.RAP_COUNTRY_ENTITLEMENT VALUES
  ('FR_ANALYST', 'US'),
  ('FR_COMPLIANCE', 'US'),
  ('FR_COMPLIANCE', 'CA'),
  ('FR_COMPLIANCE', 'UK'),
  ('ROLE_BANK_LAB_ADMIN', 'US'),
  ('ROLE_BANK_LAB_ADMIN', 'CA'),
  ('ROLE_BANK_LAB_ADMIN', 'UK'),
  ('FR_DATA_ENGINEER', 'US'),
  ('FR_DATA_ENGINEER', 'CA'),
  ('FR_DATA_ENGINEER', 'UK');
5

Write the “hide whole rows” rule

What RETURNS BOOLEAN means

For each row, Snowflake asks the policy: “May this role see this country?” TRUE = keep the row · FALSE = hide it. EXISTS (…) = “is there a matching line on the entitlement list?”

SQL · row access policy
CREATE OR REPLACE ROW ACCESS POLICY RISK_CTRL.RAP_CLIENT_COUNTRY
AS (country_code STRING) RETURNS BOOLEAN ->
  EXISTS (
    SELECT 1
    FROM RISK_CTRL.RAP_COUNTRY_ENTITLEMENT e
    WHERE e.ROLE_NAME = CURRENT_ROLE()
      AND e.COUNTRY = country_code
  );
6

Hang both rules on CLIENTS_GOV

Attach ≠ create

Until you ALTER TABLE, policies are unused paperwork. These two lines stick them on EMAIL and COUNTRY.

SQL · attach policies
ALTER TABLE CURATED.CLIENTS_GOV
  MODIFY COLUMN EMAIL
  SET MASKING POLICY RISK_CTRL.MP_EMAIL_MASK;

ALTER TABLE CURATED.CLIENTS_GOV
  ADD ROW ACCESS POLICY RISK_CTRL.RAP_CLIENT_COUNTRY ON (COUNTRY);

Let Alex’s and Sam’s key-rings read the shelf

Grants vs policies

Grant = “may you query this table at all?” Policy = “given that you can, what do you see?” Both are required.

SQL · grants
GRANT SELECT ON TABLE CURATED.CLIENTS_GOV TO ROLE AR_CURATED_READ;
GRANT SELECT ON TABLE CURATED.CLIENTS_GOV TO ROLE AR_PII_READ;

SELECT 'Lab 03 policies attached' AS status;

Proof as Alex

Why SECONDARY ROLES NONE again?

Same Lab 01 trap: without it, your lab-admin coat stays on and you see unmasked email. Policies look at CURRENT_ROLE() — primary badge only.

SQL · become Alex
USE ROLE FR_ANALYST;
USE SECONDARY ROLES NONE;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
SQL · same SELECT everyone will run
SELECT CLIENT_ID, EMAIL, COUNTRY
FROM CURATED.CLIENTS_GOV
ORDER BY CLIENT_ID;
✓ Email like ***@example.com · only US rows (no CA/UK)
