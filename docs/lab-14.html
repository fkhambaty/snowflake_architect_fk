Lab 14 · Mock interview · Drill out loud

12 scenario questions — model “Say this” answers

Read each scenario. Cover the answer in 60–90 seconds without reading verbatim. Each item links back to a lab. No Snowflake required — this is rehearsal.

How to drill
  1. Read the scenario once.
  2. Pause and answer aloud.
  3. Open “Say this” and diff your answer — note gaps.
  4. Re-run until you hit structure: context → decision → tradeoff → verify.
1

Analysts must not see SSN columns on the customer table

Maps to Lab 01 RBAC (+ masking labs if used)

Say this

“I’d use functional roles for job titles and access roles for permission packs. Analysts inherit curated-read — USAGE on database and schema, SELECT on a view that excludes SSN columns. Engineers keep raw access for pipelines. I prove it by switching to FR_ANALYST: view works, direct RAW select fails. I’d verify with SHOW GRANTS, not assume. If policy requires dynamic hiding, I’d add masking on remaining sensitive fields.”

2

Compliance wants the same query result for analysts and admins — but admins see real email, analysts see masked

Maps to Lab 03 (masking policies)

Say this

“Same view and same SQL for everyone — masking policy on the column evaluates by role. Admins get plaintext; analysts get hashed or null. APPLY MASKING POLICY is account-level, so I delegate carefully. I test with two roles on identical SELECT statements. Auditors care that we didn’t fork logic into two views unless necessary.”

3

Orders fact is 2B rows; nightly full refresh is too expensive

Maps to Lab 02, Lab 12 dbt

Say this

“Incremental dbt model on Snowflake with merge strategy and a stable unique_key like order_id. The incremental filter uses updated_at watermark from {{ this }}. I enforce a contract on the mart so downstream BI doesn’t break silently. CI runs Slim builds — state:modified+ with defer — so we don’t rebuild the whole graph every PR.”

4

Should we use Snowflake streams or dbt incremental for CDC from RAW?

Maps to Lab 04 / Lab 05 (streams & tasks)

Say this

“Streams capture change metadata in Snowflake — great for task pipelines, near-real-time, or non-dbt ops paths. dbt incremental is better when analytics engineering owns the DAG, tests, and contracts in git. Hybrid is common: stream stages deltas, dbt merges into facts on schedule. I decide based on latency SLA, team skills, and whether logic must live in SQL tasks vs dbt repo.”

5

Dashboard query scans 500GB; users complain about cost and speed

Maps to Lab 08 clustering

Say this

“I open Query Profile — partitions scanned vs total, spill to remote storage if any. If filters align with a date or tenant column, I add CLUSTER BY on that key and check SYSTEM$CLUSTERING_INFORMATION for overlap. For point lookups on IDs I might add search optimization and call out maintenance cost. I also check warehouse size and accidental Cartesian joins in QUERY_HISTORY.”

6

Query Profile shows massive spill to remote storage

Maps to Lab 08, Lab 13

Say this

“Spill means RAM on the warehouse wasn’t enough for sort/join/aggr — Snowflake used local/remote disk. Fixes: right-size warehouse up one step for that workload, reduce row width early, fix join order, cluster so less data participates. I don’t permanently upsize without profiling — I reproduce with Query Profile and measure bytes scanned and spill bytes after changes.”

7

QA team wants production-like data every sprint without doubling storage

Maps to Lab 09 clone

Say this

“Zero-copy clone schema or tables into a non-prod database — metadata pointer, not immediate full copy. QA runs on their warehouse. We refresh by re-cloning on a schedule or after masking subset rules. Clone is same-account fast fork — not geo-DR; for DR I’d talk replication in Lab 11.”

8

Partner needs read-only order metrics in their Snowflake account

Maps to Lab 10 sharing

Say this

“Secure view with minimum columns on curated facts — no raw PII table share. CREATE SHARE, grant database/schema usage, grant SELECT on the view, ADD ACCOUNTS for their locator. They query with their compute. For public catalog I’d use Marketplace; for one partner, private share is enough.”

9

Leadership asks: share vs replicate for our DR strategy?

Maps to Lab 10, Lab 11

Say this

“Share is cross-account read access to live provider objects — consumer pays compute, not our DR copy. Replication copies objects to a secondary account/region for failover — that’s DR. I’d document RPO/RTO from replication lag and failover runbook, not conflate with partner sharing. QA refresh in one account is clone, not either of those.”

10

Finance needs per-team warehouse credit chargeback

Maps to Lab 13 FinOps

Say this

“ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY aggregated by warehouse — map warehouses to teams via naming or tags. QUERY_HISTORY for attribution by user/role when disputing spikes. I tell finance views lag up to ~3 hours. Guardrails: resource monitors NOTIFY/SUSPEND, auto-suspend, separate WH per workload.”

11

Junior engineer dropped a production table; panic in Slack

Maps to Lab 09 UNDROP

Say this

“If inside Time Travel retention, UNDROP TABLE restores catalog entry and data. If they need a point before a bad UPDATE, query AT/BEFORE or clone from timestamp. Fail-safe is last resort via Snowflake support — not self-serve. Long term: replication for region loss, least privilege so drop rights are rare, and runbook drills.”

12

Board asks how we control runaway spend on ad hoc warehouses

Maps to Lab 13, Lab 12 Slim CI

Say this

“Layered controls: resource monitors with suspend at 100%, low auto-suspend seconds on ad hoc WH, query timeouts, right-sized defaults XS/S, and Slim CI so PRs don’t run full dbt builds. Technical tuning — clustering, incremental models — cuts bytes scanned. Visibility from ACCOUNT_USAGE with ownership in FinOps dashboards and alerts at 75% notify.”
