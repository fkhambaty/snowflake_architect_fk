FinOps: ACCOUNT_USAGE & resource monitors

Architects answer “who burned credits?” and “how do we cap runaway warehouses?” SNOWFLAKE.ACCOUNT_USAGE views power chargeback dashboards — with latency. Resource monitors enforce soft/hard stops on warehouse spend.

Role & latency
  • Step 1–2: use ACCOUNTADMIN (or a role with imported privileges on ACCOUNT_USAGE).
  • Views can lag ~45 minutes to 3 hours — empty or stale results on a quiet trial are normal.
After this lab you can explain
  • Warehouse metering vs query history — different questions
  • Resource monitor triggers: NOTIFY vs SUSPEND
  • Why FinOps dashboards need “as of” timestamps
1

Warehouse credit burn (last 7 days)

Understand this before you copy

ViewQuestion
WAREHOUSE_METERING_HISTORYWhich warehouses consumed credits in each interval?
SUM(CREDITS_USED)Rank warehouses for chargeback or right-sizing
Interview: tie oversized warehouse + auto-suspend policy to this query’s top row.
SQL · Step 1 · warehouse credits
USE ROLE ACCOUNTADMIN;

SELECT
  WAREHOUSE_NAME,
  SUM(CREDITS_USED) AS CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY
WHERE START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1
ORDER BY 2 DESC NULLS LAST;
✓ Expect at least WH_ARCH_XS if you ran prior labs — maybe after latency delay.
2

Expensive queries (last 24 hours)

Understand this before you copy

ColumnUse
TOTAL_ELAPSED_TIMEWall time — user pain
BYTES_SCANNEDSpill / full scan smell (with Query Profile in Lab 08)
QUERY_TEXTFind rogue cross joins or missing filters
If zero rows: say “ACCOUNT_USAGE latency” — still a valid architect answer.
SQL · Step 2 · top queries
SELECT
  QUERY_ID,
  USER_NAME,
  ROLE_NAME,
  WAREHOUSE_NAME,
  TOTAL_ELAPSED_TIME/1000 AS SECONDS,
  BYTES_SCANNED,
  QUERY_TEXT
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE START_TIME >= DATEADD('day', -1, CURRENT_TIMESTAMP())
ORDER BY TOTAL_ELAPSED_TIME DESC NULLS LAST
LIMIT 20;
3

Resource monitor on lab warehouse

Guardrail for trials and demos — adjust quota to your account.

Understand this before you copy

TriggerBehavior
ON 75 PERCENT DO NOTIFYEmail/notification — ops awareness
ON 100 PERCENT DO SUSPENDStop warehouse — prevents runaway credits
ALTER WAREHOUSE … SET RESOURCE_MONITORAttach monitor to specific compute
Monitors apply to monthly account credit pool semantics — explain NOTIFY vs SUSPEND in governance interviews.
SQL · Step 3 · resource monitor
CREATE RESOURCE MONITOR IF NOT EXISTS RM_ARCH_LAB
  WITH CREDIT_QUOTA = 10
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 100 PERCENT DO SUSPEND;

ALTER WAREHOUSE WH_ARCH_XS SET RESOURCE_MONITOR = RM_ARCH_LAB;

FinOps toolkit (talktrack)

Understand this before you copy

  • Warehouse sizing — right-size XS/S; separate ETL vs BI warehouses.
  • Auto-suspend / auto-resume — low suspend threshold for ad hoc WH.
  • Query timeout — cap pathological queries at session or account level.
  • Storage — STORAGE_USAGE, Time Travel retention cost (Lab 09).
  • Tagging — object tags for cost allocation (mention if asked).
✓

Quick self-check

  1. Why might QUERY_HISTORY miss the query you ran 10 minutes ago?
  2. What happens when a resource monitor hits SUSPEND at 100%?
  3. Metering history vs query history — different use?
Click for short answers
  1. ACCOUNT_USAGE latency (up to ~3 hours).
  2. Warehouse suspends; new queries wait until credits reset / monitor adjusted / manual resume policy.
  3. Metering: credit burn by warehouse. Query history: individual SQL tuning and attribution.
60-second interview answer
“I use ACCOUNT_USAGE warehouse metering for chargeback and query history for tuning — always noting view latency. I attach resource monitors with NOTIFY then SUSPEND on departmental warehouses. FinOps pairs with technical fixes: clustering, Slim CI, right-sized warehouses, and auto-suspend. I never tune from live queries alone on busy accounts — I use delayed views plus Query Profile.”
