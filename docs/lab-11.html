Typical flow (two accounts, business-critical feature): enable replication on source database → create replication/failover group → add secondary account → schedule refresh → document failover promotion runbook.

We paste this as reference only — running ALTER DATABASE … ENABLE REPLICATION without a secondary setup still teaches vocabulary but won’t complete DR alone.
SQL · Step 2 · reference pattern (explain, don’t require)
-- Reference architecture (two accounts + regions):
-- Primary: ALTER DATABASE ARCH_INTERVIEW ENABLE REPLICATION TO ACCOUNTS = <secondary_account_id>;
-- Create REPLICATION GROUP or FAILOVER GROUP including DBs, shares, users as needed
-- Secondary: refresh from primary; test read-only workloads
-- Failover: promote secondary when primary region unavailable (controlled event)

Quick self-check

  1. Share vs replication — one sentence each?
  2. Clone vs replication for DR?
  3. What are RPO and RTO in your own words?
Click for short answers
  1. Share: cross-account read of live objects. Replication: copy/sync objects to another account for DR or hub-spoke.
  2. Clone is same-account fast fork; replication is ongoing geo/account continuity.
  3. RPO: max acceptable data loss window. RTO: max acceptable downtime to restore service.
60-second interview answer
“For partners I use secure shares. For QA I zero-copy clone in non-prod. For DR I replicate critical databases to a secondary account/region with a failover group and tested promotion runbook. I separate RPO/RTO targets from marketing — replication lag and failover steps define what we actually get. On a single trial I validate with SHOW REPLICATION DATABASES and document the full pattern for production.”
