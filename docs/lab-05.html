Create silver CDC target table

Understand this before you copy

The task will INSERT new order events here. LOADED_AT defaults when the row lands in silver.

Separate table from Lab 04 SILVER_ORDERS — this one is append-only CDC demo.
SQL · target table
USE ROLE ROLE_ARCH_LAB_ADMIN;
USE WAREHOUSE WH_ARCH_XS;
USE DATABASE ARCH_INTERVIEW;
USE SCHEMA CURATED;

CREATE OR REPLACE TABLE ORDERS_SILVER_CDC (
  ORDER_ID NUMBER,
  CUSTOMER_ID NUMBER,
  STATUS STRING,
  ORDER_TOTAL NUMBER(12,2),
  UPDATED_AT TIMESTAMP_NTZ,
  LOADED_AT TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
);

Create append-only stream on bronze

Understand this before you copy

SQLPlain English
STREAM … ON TABLE RAW.ORDERS_EVENTSSnowflake tracks deltas since stream created
APPEND_ONLY = TRUEOnly inserts matter — good for event landing tables
Streams don’t move data by themselves — they’re a change log pointer.
SQL · stream
CREATE OR REPLACE STREAM RAW.ORDERS_EVENTS_STR
  ON TABLE RAW.ORDERS_EVENTS
  APPEND_ONLY = TRUE;
3

Create task (rare schedule — we run manually)

Understand this before you copy

SQLPlain English
WHEN SYSTEM$STREAM_HAS_DATA(…)Skip work if stream is empty
SCHEDULE = 'USING CRON …'Placeholder; lab uses EXECUTE TASK
INSERT … SELECT … FROM streamConsume stream rows into silver
Production tasks run on a real schedule; we RESUME then EXECUTE once for learning.
SQL · task definition
CREATE OR REPLACE TASK CURATED.TASK_ORDERS_CDC
  WAREHOUSE = WH_ARCH_XS
  SCHEDULE = 'USING CRON 0 0 1 1 * UTC'
  WHEN SYSTEM$STREAM_HAS_DATA('RAW.ORDERS_EVENTS_STR')
AS
  INSERT INTO CURATED.ORDERS_SILVER_CDC (ORDER_ID, CUSTOMER_ID, STATUS, ORDER_TOTAL, UPDATED_AT)
  SELECT ORDER_ID, CUSTOMER_ID, STATUS, ORDER_TOTAL, UPDATED_AT
  FROM RAW.ORDERS_EVENTS_STR;

Resume task → insert test row → execute → verify

Understand this before you copy

New stream data appears after an INSERT to the base table. Then the task drains the stream into CDC silver.

Order id 1099 is a lab-only row — easy to spot in results.

Chunk A — enable + feed stream

SQL · resume + insert
ALTER TASK CURATED.TASK_ORDERS_CDC RESUME;

INSERT INTO RAW.ORDERS_EVENTS VALUES
  (1099, 1, 'CREATED', 1.00, CURRENT_TIMESTAMP());

Chunk B — run task + check

SQL · execute + select
EXECUTE TASK CURATED.TASK_ORDERS_CDC;

SELECT * FROM CURATED.ORDERS_SILVER_CDC WHERE ORDER_ID = 1099;
✓ One row for order 1099 in ORDERS_SILVER_CDC
5

Suspend task (save credits)

Understand this before you copy

A resumed task can fire on schedule even when you’re not watching. SUSPEND stops automatic runs.

Always suspend lab tasks unless you intentionally leave a scheduler on.
SQL · suspend
ALTER TASK CURATED.TASK_ORDERS_CDC SUSPEND;

SELECT 'Lab 05 stream/task OK — task suspended to save credits' AS status;

Optional: Dynamic Table (declarative refresh)

Skip if your account edition blocks it — interview answer still works.

Understand this before you copy

Dynamic tables let Snowflake maintain a query result with a target lag — less imperative than stream+task.

SQLPlain English
TARGET_LAG = 'DOWNSTREAM'Refresh when downstream needs it (simplified)
AS SELECT … FROM RAW.ORDERS_EVENTSDeclarative pipeline body
Compare to stream/task: who owns orchestration — you vs platform.
SQL · optional dynamic table
USE SCHEMA CURATED;

CREATE OR REPLACE DYNAMIC TABLE DT_ORDERS_STATUS
  TARGET_LAG = 'DOWNSTREAM'
  WAREHOUSE = WH_ARCH_XS
AS
SELECT ORDER_ID, STATUS, UPDATED_AT
FROM RAW.ORDERS_EVENTS;

SELECT * FROM DT_ORDERS_STATUS ORDER BY ORDER_ID LIMIT 10;
SELECT 'Dynamic table created (optional path)' AS status;

Comparison: Streams/Tasks vs Dynamic Tables vs dbt

Understand this for interviews

No single winner — architects pick based on team skills, latency, and governance.

ApproachWhat it isStrengthsWatch-outs
Stream + Task Native CDC + scheduled/imperative SQL Fine-grained control, in-account, no extra orchestrator Task graphs, monitoring, suspend/resume discipline
Dynamic Table Declarative materialized pipeline in Snowflake Less boilerplate, lag-driven refresh Edition/features, debugging DAG of DTs
dbt (Lab 02) SQL transforms + tests in git, runs on warehouse Version control, testing, docs, portable pattern Needs orchestration (CI/Airflow) for near-real-time
✓

Self-check

  1. What does a stream store — full table copy or change metadata?
  2. Why SUSPEND after the lab?
  3. When would you pick dbt over a task chain?
  4. What does APPEND_ONLY assume about source changes?
Click for short answers
  1. Change tracking / delta pointers — not a second full copy of the table.
  2. Prevent scheduled task runs burning warehouse credits overnight.
  3. Rich transform testing, git review, portable analytics engineering workflow.
  4. Only inserts — not in-place updates/deletes on the source table.
Interview soundbite
“For near-real-time in Snowflake I use streams for change capture and tasks for incremental INSERT/MERGE, with SYSTEM$STREAM_HAS_DATA to avoid empty runs — and I suspend tasks in non-prod. Dynamic tables are declarative when I want lag-based refresh without hand-rolling task DAGs. dbt stays my choice for tested, versioned marts when batch latency is fine.”
