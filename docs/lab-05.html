3

Define the worker (task)

Read the task header

SCHEDULE uses a far-future cron so the task is legal but idle; WHEN + EXECUTE TASK drive the lab proof. Body reads from the stream, not the base table — that’s how you process only deltas.

SQL · TASK_TXN_CDC (definition)
CREATE OR REPLACE TASK SILVER_CURATED.TASK_TXN_CDC
  WAREHOUSE = WH_BANK_XS
  SCHEDULE = 'USING CRON 0 0 1 1 * UTC'
  WHEN SYSTEM$STREAM_HAS_DATA('BRONZE_LANDING.TXN_EVENTS_STR')
AS
  INSERT INTO SILVER_CURATED.TXN_SILVER_CDC (TXN_ID, CLIENT_ID, STATUS, AMOUNT, UPDATED_AT)
  SELECT TXN_ID, CLIENT_ID, STATUS, AMOUNT, UPDATED_AT FROM BRONZE_LANDING.TXN_EVENTS_STR;
✓ Task created (starts suspended until RESUME)

Resume the task

Why RESUME?

New tasks are suspended by default — resume so EXECUTE TASK can run the body when the stream has data.

Optional: dynamic table pattern

When Elena picks dynamic tables

Same dock, different job than Steps 1–6: no stream, no task body — declare AS SELECT + TARGET_LAG, Snowflake keeps the shelf fresh. Use the scenario picker above if you’re unsure. Jordan’s stream+task stays for custom CDC he can audit line-by-line.

SQL · context
USE ROLE ROLE_BANK_LAB_ADMIN;
USE WAREHOUSE WH_BANK_XS;
USE DATABASE MERIDIAN_BANK;
USE SCHEMA SILVER_CURATED;
SQL · DT_TXN_STATUS
CREATE OR REPLACE DYNAMIC TABLE DT_TXN_STATUS
  TARGET_LAG = 'DOWNSTREAM'
  WAREHOUSE = WH_BANK_XS
AS
  SELECT TXN_ID, STATUS, UPDATED_AT FROM BRONZE_LANDING.TXN_EVENTS;
SQL · peek dynamic table
SELECT * FROM DT_TXN_STATUS ORDER BY TXN_ID LIMIT 10;
✓ Rows mirror BRONZE_LANDING — refresh managed by Snowflake

Interviewer presses further — say these out loud

Basics got you into the room. Cover each answer before you open it. If you blank here, an Architect + dbt interviewer will know.

Q1. Streams+tasks vs Dynamic Tables vs dbt — pick for Meridian and when you’d refuse each.

Say: Stream+task for near-real-time BRONZE→SILVER CDC with explicit control (and SUSPEND so credits don’t burn). Dynamic Tables for declarative lag. dbt for governed batch marts, tests, Slim CI. Refuse tasks left resumed forever in a demo; refuse DT for heavy procedural merge; refuse dbt for sub-minute risk ticks.

Q2. Stream offsets advance on consumption — silent data-loss mode?

Say: Ad-hoc SELECT from the stream (or messy partial consume) can advance offsets outside the task. Production: task owns INSERT…SELECT from the stream; don’t “peek” the stream in worksheets. Monitor STREAM_HAS_DATA and task history for lag.

Q3. Why SUSPEND the lab task — what does prod do instead?

Say: A resumed task still wakes warehouses; leaving it running burns trial credits. Prod keeps it resumed with WHEN STREAM HAS DATA, alerting on failures, warehouse auto-suspend. Suspend is a lab seatbelt, not the architecture.

Q4. Can Dynamic Tables replace RAP/masking on Silver?

Say: No — DT moves data; policies govern reads. You can DT into a governed table and still attach RAP. Pipeline ≠ security.

Q5. Cost comparison in one sentence?

Say: Tasks bill warehouse runtime per fire; DTs bill refresh compute to meet TARGET_LAG; dbt bills WH_BANK_XS per run — pick the freshness you can afford and measure lag; don’t stack all three on the same grain.
